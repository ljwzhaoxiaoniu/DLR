本体建模效果评测框架

基于 opencode 基线化与双范式对照的标准化评测方案——
把"哪种语义建模更能引导 Agent"变成一个可量化、可复现的工程问题。

ER 92.0% RDF 89.3% 150 题 · 同条件对照

一句话定位：这不是 NL2SQL 评测——不给库，考察建模对 Agent 从理解问题到定位数据的全程引导

背景

先回答一个问题：评测为什么重要

🎯

方案选型

ER、RDF、本体……选谁？没有对照数据就是拍脑袋。语义建模工作量大，投入前需要一个客观依据。

🔬

能力归因

效果提升来自 Agent 变强还是建模变好？混在一起无法归因，也就无法迭代。

💰

资源投向

建模是一次性投入、长期收益——值不值得？需要可量化的收益证明。

⚖️ 核心逻辑：控制变量法

屏蔽大模型随机性、提示词技巧等干扰，将所有表现差异唯归因于"语义底座的组织结构"。

总体架构

评测要成立，先解决四个问题

01

Agent 是变量

大模型随机性、提示词技巧、工具用法差异，会淹没范式信号。

解法：基线化 Agent + 上层 SOP/Skill 拉齐能力下限（第一步）
02

信息不对齐

两种范式若描述详略不一，测的是"谁写得全"，而非"谁组织得好"。

解法：统一语义底座，唯一变量 = 关联结构（第二步 · 约束）
03

任务空间不具代表性

太简单测不出引导力差异；领域单一结论不普适；对错无法判定评测不成立。

解法：利用 NL2SQL 数据集满足约束（第三步 · 落实）
04

过程不可信

Agent 绕过底座直连库、多跑取最好、判定靠感觉。

解法：防作弊环境 + 全链路审计 + 人机闭环（第四步）

第一步

基线化 Agent：Agent 不是变量

🧩

轻量构建 + 启发式引导

统一 opencode 框架 + agents.md，不动底层代码。
注入自然语言规则——"强制 /mcps 发现工具"、ReAct 闭环 semantic → evidence ↔ mapping → SQL—— 引导而非死板工作流，确保所有实验中 Agent 的"智商底座"完全一致。

🛡️

上层 SOP 与领域 Skill（能力拉齐）

复杂困难题（多表 JOIN 膨胀、SQLite 整数除法陷阱）仅靠底层图检索， 可能触发 LLM 思维盲区——引入上层 SOP 指导， 拉齐 Agent 解决困难问题的下限，避免能力瓶颈掩盖范式效能。
载体：领域 Markdown（Skill）+ MCP 工具描述层提示。
公平性：通用业务 SOP 对双范式同等开放，不含任何范式 API 偏向。

🚫 防背答案铁律

知识/Skill 只写领域事实本身，禁止写对着题面的操作指令；Schema 指引不进知识层—— 否则知识库会退化成答案缓存，评测也就失效了。

第二步 · 约束

统一语义底座：五条约束

约束一 · ER 范式

数据库建模标准基线

YAML 配置：BizEntity / BizAttribute / BizRelation

关联用 from → to 扁平表达

约束一 · RDF 范式

W3C 语义网标准基线

W3C R2RML .ttl 配置：rr:TriplesMap

关联用 rr:joinCondition 编码

约束二 · 描述逐字一致

字段语义注释（ER description ↔ RDF rdfs:label/comment）内容严格对齐。

约束三 · 知识等价

Agent 看到的领域 RAG 知识库完全等价——同一份知识，双范式共享。

约束四 · 唯一变量

唯一的区别在于关联关系表达与 Entity 归属层级，纯粹考验"信息组织结构"对 LLM 的引导效能。

约束五 · 裸问

不给 db_id、不给 evidence——语义路由与知识发现成为被考察的建模能力。
这是语义建模评测区别于 NL2SQL 评测的根本： NL2SQL 给定库写 SQL；语义建模评测要求 Agent 靠语义底座自己定位数据。

第三步 · 落实 ①

利用数据集满足约束 · 选取：BIRD mini_dev 0703

📋 权威标注

每题带 question + evidence（出题人规则）+ gold SQL + difficulty 分级——对错可判定、难度可分层。

🌍 领域多样

11 库 10 领域（金融 / 体育 / 医疗 / 教育 / 娱乐 / 化学 / 技术 / 零售 / 游戏）——结论需跨业务形态验证。

⛰️ 难度覆盖

简单查询 → 多表 JOIN → 聚合统计 → 嵌套子查询——引导力在困难题上才分得出高下。

⚙️ 规模可控

500 题 + SQLite 单机直连——跑得完、成本可控、可复现。

🔑 关键改造 · 不给 db_id 落实约束五

BIRD 官方设定是"给定库写 SQL"——那是纯 NL2SQL 能力测验。本框架不给库： 语义层负责从问题定位数据库，"语义路由"成为被考察的建模能力。
这一步改造把任务从 NL2SQL 转变成语义建模评测——这是本框架与 NL2SQL benchmark 的根本区别。

第三步 · 落实 ②

改造成"模仿本体"的建模 （满足约束一/二/四）

改造前 · 裸表

原始数据集只有骨架

customers 表：CustomerID, Name, Segment, Currency…

yearmonth 表：CustomerID, Date, Consumption

Agent 看到的只是一堆列名——列的含义、归属、陷阱，全靠猜。

改造后 · 本体化的数据

ER 的实体/属性/关系 · RDF 的 TriplesMap

BizEntity Customer（进行消费行为的客户）

· Segment：客户分层（SME / LAM / KAM）

· 描述补注："name 不唯一，同名多卡"

· 描述补注："power 三态：数字 / NULL / '*'=无限"

Agent 面对的是业务概念 + 语义描述，而非裸表。

改造三件事：① 逐库将原始表结构建模为两套范式配置；② 每个字段补自然语言语义描述（值域、同名列消歧、数据特征）； ③ 双范式描述逐字一致，唯一差异 = 关联结构。
第三步 · 落实 ③

evidence 分流利用：数据 + 知识的闭环 （满足约束五/二/三）

数据集每题的 evidence（出题人规则）不直接交给 Agent（裸问），而是拆解分流：

→ 模型 description

数据语义：值域、列含义、同名列消歧

"power 三态：数字 / NULL / '*' = 无限"

→ 领域知识库（RAG）

出题人规则：术语定义、计算公式

"percentage = 有该属性项数 / 总项数 × 100"

把"白送的提示"变成"Agent 必须自己找到的知识"——检索行为本身，成为建模引导力的观测窗口。

RAG 知识库 知识是什么 · 定义/公式/规则
→
Agent 推理 检索知识 · 引导查询
→
模型底座 数据是什么 · 在哪/值域/归属
→
检索与映射互相验证：semantic → evidence ↔ mapping → SQL

🔁 RAG 是本体建模"数据 + 知识"的闭环

本体建模不只是静态结构，而是两件套——模型层描述"数据是什么"，RAG 知识库描述"知识是什么"。 Agent 在闭环内检索知识 → 引导查询数据 → 检索与映射互相验证，数据与知识联动，才构成完整的本体建模。

第三步 · 落实 ④

高难度题 → SOP 统一落地：一个翻盘故事

❌

全灭：q1042 football 双范式全 INCORRECT

题面要算比率，Agent 写出了 3/2——SQLite 的整数除法把 1.5 截成了 1。双范式栽在同一个坑里。

🔍

归因：不是建模缺陷

是 Agent 不知道 SQLite 的除法会取整。LLM 不是不会写 SQL，是不知道这个工具坑。

✅

修复：工具层加一行警告

execute_sql 工具描述加一行： "⚠️ 整数/整数截断小数，需 CAST AS REAL 或 *1.0"

🏆

翻盘：重跑双范式全 PASS

一行提示，问题消失——没有改任何建模配置。

📐 SOP 如何统一

  • 利用 difficulty 标注定位困难题，失败模式（JOIN 膨胀、整数除法、百分比分母陷阱）系统收集
  • 沉淀为一份通用业务 SOP，写入 Skill/工具层——不是每范式各写一套
  • 同一份 SOP 对双范式同等开放，无范式 API 偏向——统一 = 一份共享、两边可用
  • 效果：拉齐下限，不泄露任何题目答案

🧹 数据治理（满足约束的前提）

实测发现 20+ 处 gold SQL 缺陷（分子分母颠倒、JOIN 键写错、NULL 排序陷阱、答非所问）， 逐一独立重放验证后修正 gold cache。数据不干净，范式对照无意义——治理流程本身是框架的一部分。

"看似建模问题，实则是 SOP/工具层 UX 问题——不把变量控制死，你就不知道锅该甩给谁。"

—— q1042 翻盘给我们的最大教训
第四步

评测工程 · 防作弊环境

⚖️ 前置说明

双范式底座最终都归一化到引导 Agent 生成 SQL——统一的 execute_sql 透传执行； 比的是语义底座对 SQL 生成路径的引导效能，不是比"写 SQL 还是写 SPARQL"。

🙈 隔离范式预知

每次开局强制 /mcps 查看可用工具，不预知挂载哪种范式—— MCP 按范式自动注册工具子集，Agent 靠工具签名（如 er_semantic_query / rdf_semantic_query）适应，而非被告知。

🚪 执行通道归一

execute_sql MCP 是唯一只读薄透传通道：元数据（表结构/列/JOIN）走 MCP，数据查询走 SQL—— Agent 没有数据库直连能力，绕过底座无从谈起。

🔒 双向堵漏 · 防走捷径

架构级 · opencode deny 列表：直连库、文件读写等能绕过底座的工具路径，在权限层直接拒绝——后门堵死，捷径没有通道。

提示级 · agents.md 提示词：规则写死"禁止凭空猜测数据库名/表名/字段名，必须从 MCP 工具返回结果提取"——前门管住，捷径行为被约束。

第四步

四阶段流水线：跑题 → 解析 → Strict → Judge

①

跑题 · 全迹审计落盘

opencode 以 NDJSON 落盘每步 trace（工具调用/参数/返回），run_id 统一目录——任何数字可回溯到原始 trace，可复现、可审计。

②

解析 · 双通道模板 防 LLM 偷懒

Final Answer 必输出"答案通道 + Evidence SQL 通道"，解析只从 SQL 通道提取； Evidence SQL 单独执行必须直接返回答案值，计算必须写进 SQL。 解析失败/多 SQL/无 SQL 明确定义为 EXEC FAIL，不静默丢弃； 结果归一化（行序/列序/NULL/浮点格式），产出可 diff 的标准形态。

③

Strict 初判 · 秒级确定性门

gold cache 逐行精确比对，脚本秒级 PASS/FAIL。定位："确定对"的快筛器，不是裁判——把 LLM Judge 算力集中在歧义样本。

④

LLM Judge · 语义仲裁（五环节）

只判 strict FAIL 的行，增量断点续跑。五环节审视：语义理解 → 工具调用 → 映射选择 → SQL → 结果—— 审链路而非只看答案，这是观察"建模如何引导 Agent"的核心窗口。
证据边界：Agent 不见 evidence，Judge 可见 gold 作仲裁参照。判定口径固化：明细 ✓ / GROUP_CONCAT 全值 ✓ / 仅 COUNT ✗。

第四步

人机驱动：机器跑量，人做归因

🤖 机器做

全自动，零人工

跑量全自动（150 题 × 双范式）

strict 秒级判定

增量 judge 断点续跑

👤 人做三件事

机器给不出答案的部分

① 数据集治理：gold SQL 缺陷、evidence 伪代码——识别修正，剥离非范式噪声

② 翻盘归因：INCORRECT 根因归类四类（数据集缺陷 / SOP 缺失 / 建模结构 / LLM 极限），决定"修哪一层"——q1042 即此闭环产物

③ 口径裁决与定稿：翻盘口径固化文档，归档三级对齐（raw → CSV → 汇总），单题定稿防数字漂移

📊 评测产出 · 双指标体系

CORRECT（效果）+ token/步数（效率），共同刻画"引导效能"——汇总为 agent_stats（正确率、平均 token、步数分布）。 "看似建模问题，实则是 SOP/工具层 UX 问题"的判断，只有在这个闭环里才被识别。
