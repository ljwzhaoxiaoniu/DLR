TSM · DLR — 三级语义建模

让 Agent 在企业数据上答对

BIRD mini-dev 实证：11 个数据库、500 题 —— 500/500 正确。
每题 token 中位约 5.6 万；三级语义资产全部 git 化，可复跑复核。

是什么

TSM 把"回答一个问题要用的知识"分成三级

L1 数据源级 dlr

这个领域有什么：业务概念、落地在哪、怎么连。
检索面 = dlr_semantic_query → get_pe_mapping / get_le_attrs

L2 领域共识级 consensus

题面用词怎么算 / 怎么过滤：术语→列值、公式、口径。
检索面 = dlr_search_consensus

L3 业务逻辑级 sop

这道题怎么裁：打法、例外、陷阱。
检索面 = dlr_search_sop（按题检索，只取命中那一节）

三级覆盖的是 schema 级语义（结构 / 值域 / 粒度 / 术语 / 打法）；数据源实例级事实（"客户 38508 是谁"）不入体系——即时用 SQL 算，或经 MCP 外部取。
DLR 的定位：TSM 不限定数据源级用哪种建模方式；DLR 是我们推荐的数据源级范式（LE-PE 双层 + ARCS / PAS 两个机制）——本次实证用的就是它。

结果呈现 · 加分项

基准自带 74 处错题 —— TSM 照样答对

这 74 处，基准的 gold 答案本身有问题。典型形态：

计数对象错："多少客户"被算成"多少条记录" 缺类型转换：文本按字典序比大小 缺括号：OR 绕过了前面的过滤 时间序列被当单个数值求和 分母基数歧义：行 vs 去重实体 样本窗口：逐笔记录只有 4 天

TSM 的做法：L3 口径先行把正确读法钉死——即使与 gold 不同，给出的也是对的。

＋

为什么这是加分项

企业数据的常态就是定义混乱、口径冲突。语义层不只"描述数据"，还能仲裁口径——这是 TSM 超出普通 schema 描述的地方。
