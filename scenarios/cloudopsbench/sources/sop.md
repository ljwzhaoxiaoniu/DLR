## cloudopsbench

### When asked: "Partial Service Unreachability."

Follow the reachability chain and stop at the first thing that doesn't add up. Each stop below is a case — deal with the one you actually hit.

1. **Start from the complaint, not the cluster.** Read the caller's error logs, or probe the named service, or check its endpoints — that's what tells you what's actually unreachable. Opening with a workload scan is how you end up chasing the wrong thing. If the wording names no service, the inventory listing is the legitimate entry: the moment it names the outlier, the victim's own signal leads — its endpoints listing, or a connectivity probe on the port its Service declares (never a guessed port), or its caller-side error log — ahead of its workload state, the event surface, and any config read; if you batch, the signal leads the batch. This signal read is the chain's first evidence, not a closing confirmation.
2. **Then look at the workload, pruned.** The target's pods (the READY/phase outlier tells the story) → its owner chain (deployments / replica sets — replica counts, ready state) — the owner chain comes before the event surface and any config read (events are step 4's closure, not the opener here); if you batch, the owner chain leads the batch. What you find there decides the case:
   - **Pod stuck Pending** (`0/N nodes are available …`) → it's a node problem: **take the pod's own sheet first — `DescribeResource(pod)` carries the pending line itself and is this chain's first evidence; if you batch, the sheet leads** — then nodes listing / `GetClusterConfiguration`, find the node that blocks it (cordon, taints, capacity) — read that node's own state to close. **A Pending pod with no scheduling line at all — Node `<none>`, no `0/N nodes are available` condition — while every worker is Ready and untainted is not a node-side story: nothing has attempted to schedule it, so read the control-plane component — `CheckNodeServiceStatus(master, kube-scheduler)` — and close there (a master that is SchedulingDisabled by design is not the blocker; its scheduler being down is).**
   - **Pod never gets created** (FailedCreate / a missing reference) → it's admission: **the workload's own state comes first (the deployment: 0/N available, up-to-date) — before the event surface; if you batch, the workload state leads the batch** — then the event names the missing thing; read the template reference (`GetAppYAML`) plus the referenced object's own listing. **The event is live only if the thing it names is still missing — when the referenced object turns up present in its own listing, or the workload's pod already exists (a pod object that exists proves creation succeeded), the `FailedCreate` is setup history: drop the admission story and read why the existing pod cannot proceed.**
   - **Image pull errors** → the pull message decides the class: a registry host that won't resolve (`lookup … no such host`) → `image_registry_dns_failure` — even when the hostname looks made-up, it's still this class; a registry that resolves but rejects the reference (`manifest unknown` / tag not found) → `incorrect_image_reference`; `unauthorized` → the pull-secret side. Read the image line to confirm — rank 1 carries what the message says, not what the reference looks like. **Mount / probe errors** → the matching config face: mount / probe stanza in the template.
   - **Everything healthy but probes still fail** → it's the address layer: read the gateway's route table — `GetAppYAML` on the gateway service, the table lives in its own manifest (gateway logs, endpoints and config listings are not a substitute) — and go through it route by route — each route's Path should point at the service its Path names; one that points elsewhere is your evidence (**report the gateway — the table's owner — as the component; the mis-wired target is the victim, not the break**). When you submit: rank 1 names the gateway — the victim may sit lower in the list, never at rank 1. Stop probing — probing is confirmation, not evidence.
3. **When the chain crosses services, walk the topology before the material.** The cross-service localization evidence is `GetServiceDependencies` — and the walk's anchor is the **symptom side** (the service whose logs carried the complaint), pointed toward the suspect; an anchor anywhere else (the suspect included) is a guess, not the walk. It sits between the symptom reads and any mechanism / config / code material (a YAML, a service object, code files) — material read before the walk doesn't localize; if you batch, the walk leads the material.
4. **Close properly before you conclude — all three:** the mechanism event; the events surface (`GetResources(events)` — its Warning lines name exactly which object, and for multi-instance workloads which replica, carries the fault); and the config the mechanism points at. Mechanism-only or service-log-only conclusions aren't a closed chain.

This wording also shows up on scheduling / startup failures — decide by what you find on the chain, not by the wording.

### When asked: "Service Availability Disruption."

This wording is overloaded — it walks the SAME reachability chain whichever stage broke (scheduling / startup / admission / runtime / code). Go case by case; the mechanism decides, not the wording.

1. **Start from the complaint.** Caller-side error logs / connectivity against the named service; then the endpoints binding — for a named service, don't open with a workload scan. If the wording names no service, the inventory listing is the legitimate entry: the moment it names the outlier, the victim's own signal leads — its endpoints listing, or a connectivity probe on the port the victim's Service declares (take the port from its own spec — a remembered or guessed port proves nothing), or its caller-side error log — ahead of its workload state (replica counts / pods), ahead of the event surface, ahead of any configuration read. This signal read is the chain's first evidence, not a closing confirmation; if you batch, the signal leads the batch. A mechanism event or a config read fired ahead of it is the chain running backwards.
2. **Then the workload, pruned.** The pods (state + events) → owner chain. Node-scoped problem? Read the pods listing in its **wide form** first — the NODE column is your pointer.
3. **Deal with the case you land on:**
   **First, the pivot — localize across the call graph:** the topology walk (`GetServiceDependencies` — anchored at the **symptom side**, the service whose logs carried the complaint, pointed toward the suspect) sits between the symptom reads and any mechanism / config / code material (a YAML, a service object, code files); material read before the walk doesn't localize; an anchor anywhere else (the suspect included) is a guess, not the walk — take the walk, then the material; if you batch, the walk leads the material.
   - **Pod Pending / unschedulable** → **first take the pod's own reason** — `DescribeResource(pod)` carries the `N nodes are available…` line that names the blocker; only then the node side, and read general before specific there: nodes listing / `GetClusterConfiguration` / node events / kubelet status, then the suspected component (containerd, kube-proxy, …). The pod's reason comes before any node-side read; jumping straight at the suspected service reads out of order. **No scheduling line at all while the workers are Ready and untainted means nothing is attempting the pod — the control plane's `kube-scheduler` (`CheckNodeServiceStatus` on the master) is the read that closes.**
   - **Pod never created** → admission side: **the victim's own signal comes first — its endpoints listing, or a connectivity probe on its declared port (not a guessed one), or its caller's error log; if you batch, the signal leads the batch.** Then the event names the referenced object; template reference + object listing — **and that event is live only if the referenced object is still missing: one that turns up present in its own listing is setup history, not the mechanism.**
   - **Image pull / mount / probe errors** → the matching config face.
   - **Pod up, but the service misbehaves** — wrong results / functional errors in its own logs (argument order, bad values) → code-defect chain: take the suspect pod's sheet first (`DescribeResource(pod)` — status / restarts / image; this is the entry step here, ahead of the logs) — if you batch, the sheet leads the batch — then its error logs (the mis-computation), then localize the scope (`ListCodeFiles`) and prove it on the code surface (`GetSourceCode`). Logs before the pod sheet means the entry step was skipped. **If the suspect's own error logs come back clean, the symptom sits further along the call — a downstream callee's logs carry the malformed-request trail; read those against the walk before any code file read.** **A stale `FailedCreate` about a service account that already exists in the listing — with every workload healthy — is setup history, not the mechanism; the malformed-request trail is.**
   - **Everything healthy but probes diverge — or one service's logs fill with exceptions on requests that don't belong to it (foreign payloads / missing parameters) while its object layer reads clean** → the address layer: audit the gateway's route table — `GetAppYAML` on the gateway service; the table lives in its own manifest (logs, endpoints and config listings are not a substitute) — Path ↔ target line by line; the misroute signature is traffic arriving at a service its route Path doesn't name. The exception trail on that service is a **symptom of the misroute, not a code defect** — audit the route table before concluding one. Probing is confirmation, not scanning. **The component to report is the gateway (the table's owner) — the mis-wired target is the victim, not the break.**
4. **Close properly before you conclude — all three:** the mechanism event; the events surface (`GetResources(events)` — for multi-instance workloads the Warning row names the replica that carries it); and the config the mechanism points at.

### When asked: "Service quality degradation."

This wording lives on the metric surface — the alerts name the case, and the object layer is only the exclusion. Read the alerts first, and the case you land on decides:

1. **Alerts first.** `GetAlerts` tells you whose anomaly it is, which kind (latency / saturation / throughput / traffic), and at what scope. Unlike the reachability wordings, opening from the object layer here is not troubleshooting — the signal is in the metrics. When several alerts fire at once the case is the **primary anomaly** — the service the other alerts ripple from, carrying the runaway deviation: read the rows' shape before their size — a latency row that moves only its p90 is a partial-traffic ripple (only the traffic sharing a path with the degraded pod slowed), while the row whose p50 and p90 both move carries the delay across all of its traffic and marks the epicenter; among those both-percentile rows the epicenter carries the steepest p90 escalation, and the graph closes it (`GetServiceDependencies`): every ripple is its direct neighbor, so a candidate that would need a quiet intermediate hop is not the source. Percentages on near-zero baselines prove nothing. A saturation row counts only when it rides on that epicenter **and comes with the service's own latency rise** — a genuine resource fault shows the throttle *and* its own latency climbing together; a bare `cpu_cfs` row on a service that is not the epicenter, with no latency of its own, is collateral noise — don't out-rank the runaway deviation with it. A `LATENCY_MISSING` row ("metrics dropped to zero/NaN") is a hole the collection left in the injection window, not a service's deviation — it never names the case, so don't anchor on it. And when a whole-system network-drop sweep carries no latency row at all, the epicenter is the point every request flows through (the system's total traffic) — its collapse is the source, the rest is the ripple. Apply the branches below to the primary anomaly, not to the loudest keyword.
2. **Deal with the case you land on:**
   - **Saturation rows on one service** (`RESOURCE_SATURATION [cpu_cfs]` / `[cpu core]` / memory) → it's a resource fault on that service's pods: read its pods face (usage vs limits) to close.
   - **A constant delay riding on one service's own latency** — its p50/p90 jump by a fixed amount, its callers see the same added delay, its downstream server-side latencies stay clean, no saturation rows → `pod_network_delay`: the delay sits on that pod's network path. Don't reach for a code explanation — an artificial delay *in code* is a code-defect (a different wording, and it has to be shown from the code surface); under this wording a delay case is network-side.
   - **The same latency / packet anomaly across every pod on one node** (scope it with the pods listing's NODE column) → it's a node-scope network fault: read the node objects (conditions / node runtime services) to close.
3. **Close by excluding the object layer.** The pods / deployments / services / endpoints / nodes listings show everything else healthy — RESTARTS 0, AVAILABLE 1/1, endpoints bound, nodes Ready, no mechanism events. The anomaly lives in the metric surface; the object layer is your exclusion evidence.
