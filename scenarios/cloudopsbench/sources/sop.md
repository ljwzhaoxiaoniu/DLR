# SOP — business-logic level (read this FIRST)

> One section per **symptom wording** — the title is the wording **verbatim** (the dataset
> reuses a small set of templates, so one section covers every case that says the same thing).
> If a section restates your question, follow it: it goes case by case — deal with the branch
> your evidence lands on and stop at the first thing that doesn't add up. No match -> nothing
> known about this walk; solve with L1 (objects) + L2 (readings).
>
> This is the ops team's own playbook, written the way ops people write for each other on top
> of a stable L1/L2 — plain language, no K8s 101, no answers. A branch gets added only when
> runs show the case it covers.

## cloudopsbench

### When asked: "Partial Service Unreachability."

Follow the reachability chain and stop at the first thing that doesn't add up. Each stop below is a case — deal with the one you actually hit.

1. **Start from the complaint, not the cluster.** Read the caller's error logs, or probe the named service, or check its endpoints — that's what tells you what's actually unreachable. Opening with a workload scan is how you end up chasing the wrong thing. If the wording names no service, the inventory listing is the legitimate entry: the moment it names the outlier, the victim's own signal leads — its endpoints listing, or a connectivity probe on the port its Service declares (never a guessed port), or the entry caller's error log (the front door the request comes through) — ahead of its workload state, the event surface, and any config read; if you batch, the signal leads the batch. This signal read is the chain's first evidence, not a closing confirmation.
2. **Then look at the workload, pruned.** The target's pods (the READY/phase outlier tells the story) → its owner chain (deployments / replica sets — replica counts, ready state) — the owner chain comes before the event surface and any config read (events are step 4's closure, not the opener here); if you batch, the owner chain leads the batch. What you find there decides the case:
   - **Pod stuck Pending** (`0/N nodes are available …`) → it's a node problem: **take the pod's own sheet first — `DescribeResource(pod)` carries the pending line itself and is this chain's first evidence; if you batch, the sheet leads** — then nodes listing / `GetClusterConfiguration`, find the node that blocks it (cordon, taints, capacity) — read that node's own state to close. **A Pending pod with no scheduling line at all — Node `<none>`, no `0/N nodes are available` condition — while every worker is Ready and untainted is not a node-side story: nothing has attempted to schedule it, so read the control-plane component — `CheckNodeServiceStatus(master, kube-scheduler)` — and close there (a master that is SchedulingDisabled by design is not the blocker; its scheduler being down is).**
   - **Pod never gets created** (FailedCreate / a missing reference) → it's admission: **the victim's own signal comes first — its endpoints listing, or a connectivity probe on its declared port (not a guessed one), or the entry caller's error log; if you batch, the signal leads the batch — then the workload's own state (the deployment: 0/N available, up-to-date) — before the event surface; if you batch on, the workload state leads** — then the event names the missing thing; read the template reference (`GetAppYAML`) plus the referenced object's own listing. **A quota case closes on the `resourcequota` object itself — read its used/hard rows — and it needs no event: a quota that has been full all along leaves the event surface with no Warning at all, and a used == hard row alone is the mechanism. When what a template declares never lands — a Service the app YAML declares that is absent from the namespace's own service listing — that absence is the effect, not the fault: read the namespace's `resourcequota` (its `services` used/hard row) before any resolution story. A Service that was never created is what kills its name lookup, so a missing Service object is never `service_dns_resolution_failure` — used == hard closes the case as the namespace's service quota (`namespace_service_quota_exceeded`; report the namespace). **And keep the chain's order: the victim's signal read still leads — the declared-vs-live listing comes after it, in its own step, never in its place; the quota rows close after the listing. If you batch, the signal leads the listing, and the listing leads the quota.** **The event is live only if the thing it names is still missing — when the referenced object turns up present in its own listing, or the workload's pod already exists (a pod object that exists proves creation succeeded), the `FailedCreate` is setup history: drop the admission story and read why the existing pod cannot proceed.**
   - **Image pull errors** → the pull message decides the class — the failing stage in the message is the discriminator; read it verbatim: the request never reaches the registry (`failed to do request … lookup … no such host`) → `image_registry_dns_failure` — even when the hostname looks made-up, it's still this class; the registry answers on the manifest itself (`rpc error: code = NotFound` / `manifest unknown`; a mirror's bare 403 on the HEAD manifest of a bogus tag counts here) → `incorrect_image_reference`; the failure sits at the registry's **token step** (`failed to authorize: failed to fetch anonymous token: … /token…: 403 Forbidden` — the rejection comes from the token endpoint, whatever its 401/403) → `missing_image_pull_secret` — that is the credential side, not the reference; the workload template's `Image pull secrets: <none>` corroborates it. Rank 1 carries what the message says, not what the reference looks like. **Mount / probe errors** → the matching config face: mount / probe stanza in the template.
   - **Everything healthy but probes still fail** → it's the address layer: read the gateway's route table — `GetAppYAML` on the gateway service, the table lives in its own manifest (gateway logs, endpoints and config listings are not a substitute) — and go through it route by route — each route's Path should point at the service its Path names; one that points elsewhere is your evidence (**report the gateway — the table's owner — as the component; the mis-wired target is the victim, not the break**). When you submit: rank 1 names the gateway — the victim may sit lower in the list, never at rank 1. Stop probing — probing is confirmation, not evidence.
3. **When the chain crosses services, walk the topology before the material.** The cross-service localization evidence is `GetServiceDependencies` — and the walk's anchor is the **symptom side** (the service whose logs carried the complaint), pointed toward the suspect; an anchor anywhere else (the suspect included) is a guess, not the walk. It sits between the symptom reads and any mechanism / config / code material (a YAML, a service object, code files) — material read before the walk doesn't localize; if you batch, the walk leads the material.
4. **Close properly before you conclude — all three:** the mechanism event; the events surface (`GetResources(events)` — its Warning lines name exactly which object, and for multi-instance workloads which replica, carries the fault); and the config the mechanism points at. Mechanism-only or service-log-only conclusions aren't a closed chain.

This wording also shows up on scheduling / startup failures — decide by what you find on the chain, not by the wording.

### When asked: "Service Availability Disruption."

This wording is overloaded — it walks the SAME reachability chain whichever stage broke (scheduling / startup / admission / runtime / code). Go case by case; the mechanism decides, not the wording.

1. **Start from the complaint.** Caller-side error logs / connectivity against the named service; then the endpoints binding — for a named service, don't open with a workload scan. If the wording names no service, the inventory listing is the legitimate entry: the moment it names the outlier, the victim's own signal leads — its endpoints listing, or a connectivity probe on the port the victim's Service declares (take the port from its own spec — a remembered or guessed port proves nothing), or the entry caller's error log (the front door the request comes through) — ahead of its workload state (replica counts / pods), ahead of the event surface, ahead of any configuration read. This signal read is the chain's first evidence, not a closing confirmation; if you batch, the signal leads the batch. A mechanism event or a config read fired ahead of it is the chain running backwards.
2. **Then the workload, pruned.** The pods (state + events) → owner chain. Node-scoped problem? Read the pods listing in its **wide form** first — the NODE column is your pointer.
3. **Deal with the case you land on:**
   **First, the pivot — localize across the call graph:** the topology walk (`GetServiceDependencies` — anchored at the **symptom side**: the service whose own log carries the failing business call, the outermost caller's trail — the entry the failed action came through — pointed toward the suspect) sits between the symptom reads and any mechanism / config / code material (a YAML, a service object, code files); material read before the walk doesn't localize; an anchor anywhere else (the suspect included, an alert-flagged service included) is a guess, not the walk — take the walk, then the material; if you batch, the walk leads the material. **If your first walk anchored elsewhere, the repair is one call: take it again from the symptom side once that log is in hand.**
   - **Pod Pending / unschedulable** → **first take the pod's own reason** — `DescribeResource(pod)` carries the `N nodes are available…` line that names the blocker; only then the node side, and read general before specific there: nodes listing / `GetClusterConfiguration` / node events / kubelet status, then the suspected component (containerd, kube-proxy, …). The pod's reason comes before any node-side read; jumping straight at the suspected service reads out of order. **No scheduling line at all while the workers are Ready and untainted means nothing is attempting the pod — the control plane's `kube-scheduler` (`CheckNodeServiceStatus` on the master) is the read that closes.**
   - **Pod never created** → admission side: **the victim's own signal comes first — its endpoints listing, or a connectivity probe on its declared port (not a guessed one), or the entry caller's error log; if you batch, the signal leads the batch.** Then the event names the referenced object; template reference + object listing. **Quota cases close on the namespace `resourcequota` object's used/hard rows — an all-Normal event surface does not rule them out; and when a declared Service is absent from the live service listing, read that quota (`services` used/hard) before any resolution story — a Service that never landed kills its own name lookup, so a missing Service object is never `service_dns_resolution_failure` (used == hard → `namespace_service_quota_exceeded`; report the namespace). **And the signal still leads here: listing and quota reads come after the victim's signal read, never in its place; if you batch, the signal leads the listing, and the listing leads the quota.** **And that event is live only if the referenced object is still missing: one that turns up present in its own listing is setup history, not the mechanism.**
   - **Image pull errors** → the pull message decides the class — the failing stage is the discriminator; read it verbatim: `failed to do request … lookup … no such host` → `image_registry_dns_failure` (a made-up hostname is still this class); the manifest request itself rejects (`NotFound` / `manifest unknown`; a mirror's bare 403 on the HEAD manifest of a bogus tag counts) → `incorrect_image_reference`; the registry's token step rejects (`failed to authorize: failed to fetch anonymous token: … 403 Forbidden`) → `missing_image_pull_secret` — the credentials side, not the reference (the template's `Image pull secrets: <none>` corroborates). Rank 1 carries what the message says, not what the reference looks like. **Mount / probe errors** → the matching config face.
   - **Pod up, but the service misbehaves** — wrong results / functional errors in its own logs (argument order, bad values) → code-defect chain: take the suspect pod's sheet first (`DescribeResource(pod)` — status / restarts / image; this is the entry step here, ahead of the logs) — if you batch, the sheet leads the batch — then its error logs (the mis-computation), then localize the scope (`ListCodeFiles`) and prove it on the code surface (`GetSourceCode`). Logs before the pod sheet means the entry step was skipped. **If the suspect's own error logs come back clean, the symptom sits further along the call — a downstream callee's logs carry the malformed-request trail; read those against the walk before any code file read.** **A stale `FailedCreate` about a service account that already exists in the listing — with every workload healthy — is setup history, not the mechanism; the malformed-request trail is.** **On the code surface, the two look-alike code classes part by what the defect line itself does — not by the words the error message uses: a request field blanked before it goes to work (the lookup or outgoing call the field feeds sees an empty value, and the error echoes that empty field — an id or a currency that came through empty) is `code_missing_parameter`; a handler whose own return path rejects or fails a request that arrived complete (its error complains about a field the caller did send — "not specified" for an id that was specified) is `code_wrong_return`. Read the defect line; rank by it.**
   - **Everything healthy but probes diverge — or one service's logs fill with exceptions on requests that don't belong to it (foreign payloads / missing parameters) while its object layer reads clean** → the address layer: audit the gateway's route table — `GetAppYAML` on the gateway service; the table lives in its own manifest (logs, endpoints and config listings are not a substitute) — Path ↔ target line by line; the misroute signature is traffic arriving at a service its route Path doesn't name. The exception trail on that service is a **symptom of the misroute, not a code defect** — audit the route table before concluding one. Probing is confirmation, not scanning. **The component to report is the gateway (the table's owner) — the mis-wired target is the victim, not the break.**
4. **Close properly before you conclude — all three:** the mechanism event; the events surface (`GetResources(events)` — for multi-instance workloads the Warning row names the replica that carries it); and the config the mechanism points at.

### When asked: "Service quality degradation."

This wording lives on the metric surface — the alerts name the case, and the object layer is only the exclusion. Read the alerts first, and the case you land on decides:

1. **Alerts first.** `GetAlerts` tells you whose anomaly it is, which kind (latency / saturation / throughput / traffic), and at what scope. Unlike the reachability wordings, opening from the object layer here is not troubleshooting — the signal is in the metrics. When several alerts fire at once the case is the **primary anomaly** — the service the other alerts ripple from, carrying the runaway deviation: read the rows' shape before their size — a latency row that moves only its p90 is a partial-traffic ripple (only the traffic sharing a path with the degraded pod slowed), while the row whose p50 and p90 both move carries the delay across all of its traffic and marks the epicenter; among those both-percentile rows the epicenter carries the steepest p90 escalation (measured baselines only), and the graph closes it (`GetServiceDependencies`). Then settle the pick in this order — branches (a) then (b):
   - **(a) Two moving rows on one call path:** if one moving row's service sits downstream of another moving row's service on the walk, **the downstream one is the source — whatever the row shapes say**: the upstream row is its accumulated wait on the callee, and a leaf that moves only its p90 is a delay riding the leaf's own path (the p90-only-is-ripple reading is for rows with no moving row downstream of them). This also settles a zeroed-baseline pair (`New Spike`, nothing else to rank by) — the downstream one is the source.
   - **(b) Independent candidates (no call path between them):** every ripple is its direct neighbor, so a candidate that would need a quiet intermediate hop is not the source; the dual-moving row is the epicenter and a p90-only row is a partial-traffic ripple — among the dual rows the steepest p90 escalation takes it. Percentages on near-zero baselines prove nothing. A saturation row counts only when it rides on that epicenter **and comes with the service's own latency rise** — a genuine resource fault shows the throttle *and* its own latency climbing together; a bare `cpu_cfs` row on a service that is not the epicenter, with no latency of its own, is collateral noise — don't out-rank the runaway deviation with it. **And when no latency row is in the set at all — the alerts read as bare saturation — the case is not on the saturation surface: a `Val: … (Throttled)` with no normal to compare against shows no movement (a chronically throttled value reads the same before and after), and sub-core percentages are sub-noise; the row that carries an actual deviation beyond saturation — a traffic / network move — is the one that names the service.** A `LATENCY_MISSING` row ("metrics dropped to zero/NaN") is a hole the collection left in the injection window, not a service's deviation — it never names the case, so don't anchor on it. And when a whole-system network-drop sweep carries no latency row at all, the epicenter is the point every request flows through (the system's total traffic) — its collapse is the source, the rest is the ripple. **Client-side fallout during the sweep — resolution errors in a client's startup logs (`host not found in upstream …`), a client restarting — rides the same sweep: the class stays the network-side delay on the total-traffic point; a resolution-looking message inside the sweep does not make a DNS case.** Apply the branches below to the primary anomaly, not to the loudest keyword.
2. **Deal with the case you land on:**
   - **Saturation rows on one service** (`RESOURCE_SATURATION [cpu_cfs]` / `[cpu core]` / memory) → it's a resource fault on that service's pods: read its pods face (usage vs limits) to close.
   - **A constant delay riding on one service's own latency** — its p50/p90 jump by a fixed amount, its callers see the same added delay, its downstream server-side latencies stay clean, no saturation rows → `pod_network_delay`: the delay sits on that pod's network path. Don't reach for a code explanation — an artificial delay *in code* is a code-defect (a different wording, and it has to be shown from the code surface); under this wording a delay case is network-side.
   - **The same latency / packet anomaly across every pod on one node** (scope it with the pods listing's NODE column) → it's a node-scope network fault: read the node objects (conditions / node runtime services) to close.
3. **Close by excluding the object layer.** The pods / deployments / services / endpoints / nodes listings show everything else healthy — RESTARTS 0, AVAILABLE 1/1, endpoints bound, nodes Ready, no mechanism events. The anomaly lives in the metric surface; the object layer is your exclusion evidence.

### When asked: "Service latency increased significantly"

This wording lives on the metric surface — alerts first. A wave of latency and traffic drops across several services at once is usually a node-scope network story: localize by placement, not by the loudest row.

1. **Open wide, then place.** Read the pods listing in its **wide form** — the NODE column is your map — together with the alerts (and the error-log trail, for service names, if it is cheap). The degrading services' pods landing on one node names the case: that node's network. One service degrading alone is its own pod story; several services that share a node is the node's story.
2. **The node retransmission rows decide, in this order.** ① Compare the node retransmission values: when one node's value is far above every other (an order of magnitude or more), that node is the case — and retransmissions there are **packet loss**: the class is `node_network_packet_loss`. ② When no node carries a prominent retransmission value — only noise-sized spikes, wherever they sit — the case is a network **delay**: the node is the placement pick from step 1, and a small spike on another node does not move it.
3. **Close on the node surface** — the node's own objects / `GetClusterConfiguration` — with the placement map (which service pods sit on that node) as the localization evidence.

### When asked: "Service Performance Degradation."

This wording can hide a code defect under a resource-shaped alert. When one service shows saturation (cpu climbing, `cpu_cfs` throttling) with its own latency climbing and a burst of 503s across its business actions, the metric surface has named the symptom, not the mechanism.

1. **Clear the code surface of the flagged service before ranking any resource class.** `ListCodeFiles` → `GetSourceCode` on that service. Run-away work can live in its own request handler — a hot loop doing work the request does not need burns cpu and throttles the pod exactly the way an overload would.
2. **Then close:** a defect line on the code surface is your mechanism (a code class, not a resource class); only when the code reads clean is the resource face (pods: usage vs limits) yours to report.
