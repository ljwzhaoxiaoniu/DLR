背景 · 问题

文本没有稳定 schema，层级只在使用中成立

同一句话，在不同场景里可能是断言，也可能是规则。层级不在文字里，在读它的人把它当什么用。

冻结派 · W3C 本体工程

把每条知识铸死成公理或个体

  • 业务人员读不懂，维护无人接手
  • 处于 LLM 语料分布边缘，机器性能最差
  • 四十年，一场没跑通
放任派 · 裸 RAG

所有文本块平等检索，不分层

  • 每次召回都在临时赋型，检索器不自知
  • 手册全文和一句口径共识同等待遇
  • 层级混乱、口径打架、token 爆炸
三类资产，三种欠账：数据欠“这数据是什么意思”；知识欠“该站哪一层、谁签字”；API 欠“调用契约的人话”。语义化不是重新建模，是补一笔四十年的欠账。
处方

以数据架构为纲：认领，不发明

纲是出发点，不是圣经

语义层不擅动 schema，但对 schema 的描述享有 correction 权：表还是那张表，可以写“此表名为 X 实为 Y，按 Z 理解”。

纲不殖民血肉

实例文本亿级、持续膨胀；语义骨架千级、稳定。体系只存“去哪类”的路由条目，内容留在业务系统，运行期再拉取。

不发明、不补全、不重建

不凭空构建本体，不以知识完备为目标，不为还没产生的数据建模。资产不换，只补说明。

语义层的使命：把现有 ICT 资产——数据、知识、API——语义化，从 ready to machine 到 ready to human。

概念 · TSM

三级语义建模：按“谁维护、什么时候变”分层

L1 · dlr

数据源级

这个领域有什么：业务概念、落在哪、怎么连。

维护：数据侧 · 随 schema / 数据源演进
L2 · consensus

领域共识级

题面用词怎么算、怎么过滤：术语→值、公式、口径、背景。

维护：领域业务人员 · 随业务口径
L3 · sop

业务逻辑级（SOP）

这类问题怎么裁：打法、例外、陷阱、链序纪律。

维护：业务人员 · 随流程 / 打法
别混：TSM 是三级框架；DLR 是 L1 的一种实现（本项目原创），不是三级的统称。L2 = 领域共识（consensus），L3 = SOP（sop）。
“这个数据怎么存” → L1 “这句话查什么列 / 怎么算” → L2 “这种题容易怎么错” → L3
实现 · DLR

DLR：物理表 → 视图 → 业务实体

物理表列 / 行 / 外键
── ARCS ──▶
PE · 视图锚 / 行空间 / 列选择 / 语义
── 1:N ──▶
LE · 业务实体可指认对象 + public 面
── PAS ──▶
另一个 LE沿谓词导航

ARCS：纵向锚定

把物理表投影成视图：A 锚定键、R 行空间、C 列选择、S 语义补注。碎表、宽表、关联表对 Agent 透明。

PAS：横向路由

LE 之间只声明“关联存在 + 起点坐标”，路径由 Agent 找。模型给导航语义，不给执行计划。

public / private

核心度量、高频过滤列升 public，进 LE 面与向量；其余留在 PE，下探可见。影响效率，不影响正确性。

消歧链：物理表的歧义由 PE 消解；PE 的歧义由 LE 消解。LE 必须是可指认的业务对象——说出名字就知道在说谁。
方法 · 核心原则

一层解决不了的，不在这一层死磕

每层只解决本层能客观判定的歧义；解决不了，向上开一层。硬压会把问题挤到另一层弹回来——按下葫芦浮起瓢。

层内 · DLR 的两级消歧

物理表 → PE → LE

物理表天然有歧义：碎表、宽表、同名异义列、多槽位 FK。PE 用视图消歧；PE 仍有歧义，LE 用“可指认对象 + public 面 + PAS”消歧。

层间 · 三级向上开

L1 → L2 → L3

L1 只回答“数据怎么存”；题面用词 ↔ 模型的映射归 L2；L1 + L2 的真实业务冲突或系统级冲突，归 L3 做题级裁决。

L3 内部再分层（COB 实证）：SOP 若只有“一层”——一节直接给一个答案——同样会歧义。SOP 分层 = 措辞层 → 分支层 → 收口层；5 节因此能覆盖 754 例。
前瞻：L2 也会随 LE 分层。全局成立的 SOP 口径可自然下放到 L2；只在某个 LE 内成立的口径按 LE 隔离。“分层消歧”与“按 LE 隔离”是同一治理工具的两种用法。

L3 · SOP 分层

5 节 SOP，为什么能覆盖 754 例

节标题 = 题面症状措辞，逐字命中；节内不是一条答案，而是一棵按证据走的分支树。

Partial Service Unreachability. Service Availability Disruption. Service quality degradation. Service latency increased significantly Service Performance Degradation.
信号先行
→
剪枝工作负载
→
机制分支
→
收口三件套
分支：Pending / 镜像拉取 / 准入 / 路由 / 代码缺陷 ……　｜　收口：机制事件 + 事件面 + 配置

为什么不是“只写答案”

同一症状措辞下可能是多个机制。节只锁定“哪一族”，具体分支由链上实际观测决定——这就是 SOP 分层。

链序是硬约束

EOC 是严格单遍级联：链头倒位，整条证据链会塌到 1/4。L3 的主体不是结论，是走链纪律。

边界 · 下一步

契约在内，实现在外

明确不做

不做什么

  • 不做本体 / KG 平台——只有 LE / PE / ARCS / PAS 四个概念
  • 不替代指标计算平台——只做“LLM 能不能正确落到你的数据上”的接地层
  • 不锁模型、不锁宿主——MCP 是标准，dsh 是首选宿主
企业扩展层

企业在哪接

  • execute_sql → DSL_SQL 服务：受控 DSL → 各方言 SQL + 权限下推（OData 参照）
  • 图后端 → 企业自建连接器，按同一读取接口实现
  • 建模 → introspect → 草稿 → 评审，接企业元数据平台

下一步 · L2 分层

L2 随 LE 分层 / 按 LE 隔离；全局成立的 SOP 口径下放到 L2。

下一步 · 新场景

用第三个真实企业数据域验证“换场景”与层重跷跷板。

下一步 · 开发态

introspect → 草稿 → 评审，让建模从手写 YAML 走向半自动。

语义层不是一座楼，
是一条制度。
