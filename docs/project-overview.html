背景

现有建模并非为 Agent 语义理解 而设计

ER 实体-关系模型

1976 年 · Peter Chen

设计初衷是面向数据库设计——帮人画 ER 图、建表、定外键。 实体、属性、关系这些概念服务于 schema 设计阶段的工程师， 并不是为了让 LLM Agent 理解数据含义而构建的。

RDF / R2RML

W3C 语义网标准

设计初衷是面向形式化推理——在 LLM 出现之前， 通过 SPARQL 和逻辑推理引擎在知识图谱上进行符号推理。 flat triple 模型没有属性归属概念，Agent 从三元组中无法判断哪个字段更重要。

🔍 语义穿刺项目很多，但缺少什么？

Text-to-SQL、KG-enhanced LLM、Schema Linking 等方向都在探索"语义"， 但大多止步于单点改进或特定 benchmark 的数字提升。 缺少一套系统的工程化评测框架—— 能够同构对比不同建模范式，将建模质量从 Agent 能力中剥离出来单独衡量。

🎯 本项目做了两件事

1. 提出 DLR——LE-PE 双层解耦模型，设计目标就是对 Agent 友好： 逻辑层说人话，物理层锚定真实数据，PAS 语义路由在概念之间导航。
2. 构建了一套工程化评测框架——三范式同构对比、Agent 归一化、 四阶段流水线（含 LLM Judge），让"哪种建模范式更好"变成一个可量化、可复现的工程问题。

三种范式

同一套数据，三种建模哲学

ER 范式

数据库建模标准基线

经典实体-关系模型：BizEntity 是业务实体，BizAttribute 是属性， BizRelation 是实体间关联。Agent 通过实体→属性→关系的层级探索来定位数据。

核心模型：BizEntity / BizAttribute / BizRelation
MCP 工具：11 + execute_sql

★ DLR 范式

原创 LE-PE 双层解耦模型

逻辑实体（LE）承载业务概念及其自然语言描述， 物理实体（PE）锚定真实表列，通过 ARCS 挂在 LE 下。 PAS 在 LE 之间建立带方向的谓词桥， 碎表/关联表作为 PE 聚合到 LE，Agent 只看业务对象。

核心模型：LE / PE / PAS / ARCS
MCP 工具：21 + execute_sql

RDF 范式

W3C R2RML 标准基线

W3C 标准 R2RML 映射：TriplesMap 将表映射为三元组， SPARQL 查询语义。标准完备但扁平 triple 模型无属性归属， JOIN 通过 joinCondition 显式列名表达。

核心模型：rr:TriplesMap + rdflib SPARQL
MCP 工具：7 + execute_sql

DLR 机制

LE-PE 双层解耦：ARCS 纵向锚定 + PAS 横向路由

LE: Customer 业务概念 · 客户
← PAS "generates" 1:N →
LE: Consumption 业务概念 · 消费行为
↓ ARCS（锚定键+列映射+语义补注）                     ↓ ARCS
PE: Customer customers 表
PE: YearMonth yearmonth 表
PE: Transaction transactions_1k 表

ARCS：LE ↔ PE 纵向锚定

ARCS（Anchor-Row-Column-Semantic）将物理实体锚定到逻辑实体。 一个 LE 可聚合多个 PE——碎表对 Agent 透明，Agent 看到的是一棵完整的业务实体树。 A=锚定键、R=行过滤、C=列映射、S=语义补注。

PAS：LE ↔ LE 横向路由

PAS（Predicate-Attribute-Semantic）是逻辑实体之间的语义路由。 带方向的谓词桥（如 Customer generates Consumption）， Agent 沿 PAS 在业务概念之间导航，如同在概念图上行走。

public / private 属性分层

public：业务核心度量列（如 Consumption、Spending），Agent 在 LE 层直接可见
private：内部 ID、技术字段，留在 PE 层，不暴露给 Agent，避免噪音干扰
PAS 的锚定键必须在源 LE 端有 public_attributes 条目，否则 Agent 断头。

🎯 LE-PE 解耦的业务意义

DLR 将建模拆为两层：业务人员定义 LE 和关键 PE 属性（"这个业务概念有哪些核心度量"）， IT 人员一次性完成 PE→物理表的 ARCS 锚定。此后建模维护完全在概念层，不碰底层表结构。
vs ER：建模即定义物理实体和关系，业务人员被迫理解表结构——本质是 IT 视角
vs RDF：需 W3C/R2RML/SPARQL 专业知识，非 IT 难以参与

🔒 变量隔离

Agent 推理引擎、AGENTS.md 规则、execute_sql 透传、LLM Judge 仲裁逻辑 —— 全部共享。每次评测，Agent 只连一个范式的 MCP Server， 看到的工具签名由该范式的建模决定。范式差异被 MCP 工具层屏蔽， Agent 不需要"知道"自己用的是哪种范式。

🎯 建模是唯一自变量

同一道题、同一个 Agent、同一套基础设施，唯一的差异是： 数据用 ER / DLR / RDF 哪种范式建模。 这意味着 Agent 的正确率差异、Token 消耗差异、工具调用路径差异， 都可以归因于建模范式的优劣——不存在"Agent 对这个范式更熟"的混淆因素。

不是比"谁 SQL 写得好"，而是在测：同样一个 Agent，拿到不同范式描述的数据后，

定性分析

DLR 为什么赢——三个关键机制

🔗

PAS 语义桥：一步定位

ER 需要 Agent 自己探索实体→属性→关系的多跳路径； DLR 通过 PAS 谓词桥直接告诉 Agent"客户产生消费行为"， 从问题到数据一步到位。
例：q1338 DLR 7K token 一击命中，ER 需 79K 多轮探索。

🎯

public 属性归属：过滤噪音

RDF flat triple 模型下两张表的字段视觉权重相等， Agent 容易被无关列吸引。DLR 的 public_attributes 只暴露业务核心度量，屏蔽魔鬼数字和内部 ID。
例：q1529 RDF 选错表走 transactions_1k，DLR LE.Consumption 属性直接引导走 yearmonth。

🗜️

PE 聚合：去掉虚构实体

纯 junction 表（多对多关联）不需要独立 LE —— 直接作为 PE 挂到业务 LE 下， 连接键升为 public。Agent 不再看到 disp、hero_power 等中间件， 只看到有意义的业务对象，消除 ER 中多出来的"维度实体"。

🏗️

LE 概念层：Agent 看到的是业务，不是表

LE 的描述是自然语言——"客户是进行消费行为的个人或组织"—— 而非 "customers 表有 CustomerID, Name, Segment 列"。 LLM 在自然语言空间里推理，LE 的表达与 LLM 的理解模式天然对齐。
