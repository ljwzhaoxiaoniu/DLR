# 背景与主张：语义层完整论述（从诊断到处方）

> **定位**：四篇叙事的 **① 背景与主张**——当前的问题（数据 / 知识 / API）+ 分析，引出主张：**语义建模以结构化数据源为基础**。
> 主张的实现：**② 概念 → [02-concept.md](02-concept.md)** ｜ **③ 实现 → [03-design.md](03-design.md)** ｜ **④ 落地 → [04-application.md](04-application.md)**。
> 本文是思考的起点，**不求完备**——未尽处由后三篇补。

## 第一部分：诊断——文本数据没有稳定的 schema
### 1.1 从 TBox/ABox 说起：结构化世界的层级是被强制的
描述逻辑里有个基本区分：**TBox**（术语层：什么是类、概念之间什么关系）和 **ABox**（断言层：某个具体个体如何如何）。这套区分之所以在形式体系里稳定工作，关键不在概念设计得巧，而在一个常被略过的前提——**归属是语法决定的**：一条表达式是公理还是断言，写出那一刻就冻结了，推理机按归属分派规则处理。
关系数据库把这个机制做得更硬：DDL 永远是术语层，表里的行永远是断言层，DBMS 在写入时**物理性地执行这个分界**（schema on write）。所以：
> **结构化数据的 TBox/ABox 归属是数据的内在属性，写入时刻终身定型，机器强制执行。**
### 1.2 文本没有这个内在属性
看一句话在不同场景里的遭遇：
> **“重过载超过 105%，先报装扩容，再考虑切负荷。”**
- **场景一**：这句话写在某线路 77 号变压器一月的检修记录里。此刻它是**一条断言**——关于某台具体设备、某次具体处置的记录，说完这件事，使命完成。
- **场景二**：调度中心把这句话收进处置规则库，标注为“重过载场景的标准动作”。还是这句话，现在它是**一条规则**——不再属于那台变压器，而是这个领域所有重过载场景都要遵循的口径。
- **场景三**：新一代变压器阈值是 110%。这句话又降回来——变成“旧标准 105，**新设备例外**”，重新成为关于具体个体的断言。
同一个字符串，三次出场，两次换层。而文本自身没有任何标记告诉你在哪个场景它站在哪一层——**它的层级不在文字里，在读它的人把它当什么用**。用形式化的行话说：
> **文本是 schema-on-read 的，每次读取由使用场景临时赋型；结构化数据是 schema-on-write 的，写入时刻终身定型。这就是文本数据和结构化数据最本质的相通处与分界点。**
一份 A320 维修手册同理：在“维修场景该查手册”的路由里它是**个体**；当有人问“襟翼检查的一般原则”，手册里的段落被当成**领域通用做法**引用——它在 TBox/ABox 之间合法地来回横跳。
### 1.3 语义建模的真正难点由此确定
层级归属这个问题，**在文本自身里没有答案，答案只在使用方式里**——被引用的频率、覆盖的范围、变更的节奏、维护的主体。所以语义建模的难点从来不是“把文本形式化”的能力问题，而是“每条知识该站哪一层”的赋型问题——这个问题没有内容侧的答案，只有使用侧的答案。
### 1.4 两种对称的失败
横跳不可消除（它是场景的真实需求）。对它的两种处理方式各死一遍：
- **冻结派（W3C 本体工程）**：把每条知识铸死成公理或个体，永不换层。铸死那一刻就错了，错误在别的场景才暴露。加上双重死因：OWL 形式记法业务人员完全读不懂（维护无人接手）、处于 LLM 语料分布边缘（机器性能最差区）——**对两个受众同时是绝境**。四十年，一场没跑通。
- **放任派（裸 RAG）**：不分层，所有文本块平等检索。每次召回都在临时赋型而检索器不自知——手册全文和一句口径共识同等待遇挤进上下文，层级混乱、口径打架、token 爆炸。
一个把流动铸死，一个把流动放任。都不是解。
### 1.5 历史佐证：结构化赢下了每一场正面战场
- **NoSQL 反叛**：键值库在应用层手写外键，文档库发明 `$lookup`，图数据库把外键做成头等公民，Hadoop 绕一大圈终点站是 Hive——在半结构化文件上重建 schema 和 SQL。没有 schema 就没有查询，没有查询就没有价值。每次“摆脱结构”的反叛都以在更高一层重建结构告终。
- **Codd 的减法 vs W3C 的加法**：两个体系都自称形式逻辑。Codd 问“业务运转最少需要哪些逻辑运算”，答案是一小撮算子——可判定、可优化、可进硬件；W3C 问“世界的表达最多需要多少逻辑”，答案是无底洞——不可判定、无法落地。**结构化是唯一被滴定到工业可用剂量的形式逻辑。**
- **四十年建模实践是预付的判断**：ER 图、维度模型、数据标准、命名规范——每一处都是别人替你付过学费的语义沉淀。字段名是业务命名法的结晶，约束是业务规则的可执行化，主外键是关系模型的物化。**schema 是预付的判断，文本是待付的判断**——这就是“结构化信息密度最高”的严格含义（密度 = 每字节的已验证判断，不是每字节的比特）。
## 第二部分：处方——以数据架构为纲
### 2.1 为什么参照系只能是数据架构
横跳是“使用相对”的——相对就需要参照系。参照系必须满足三个条件：**长期稳定、唯一标识、机器可指**。把候选摆出来：
- 行业本体/知识图谱：W3C 四十年证明建不起来、维护不动，出局；
- 新建企业级本体：同一件事换名字重来，出局；
- 裸 LLM 隐式建模：模型换代即作废，不可审计，出局；
- **数据架构（库表、主外键、实体、主数据）**：唯一一个**已经存在、稳定运行几十年、唯一标识、机器可指**的候选。
它不需要“建”，只需要“认领”。不是它完美，是它是唯一现成的——**它的学费四十年前就付完了**。信息密度最高、变更最慢（年度节奏，当参照系刚好）、业务人员和 LLM 双受众亲和（共享母语）。
### 2.2 “为纲”的两条纪律
**纪律一：纲是出发点，不是圣经。** 存量建模是当年经济约束的产物，里面有历史失真——为了查询性能的反范式拆表、为了报表方便造的伪关联、“被迫吸收的业务上不存在的关系”。语义层不擅自动 schema，但对 schema 的描述享有 **correction 权**：表还是那张表，但语义层可以写“此表名为 X 实为 Y，历史原因，按 Z 理解”。**译者不改编原著，但译者有资格指出原文的笔误。**
**纪律二：纲不殖民血肉，血肉不淹没纲。** 实例文本（手册、参数表、图纸）亿级、多模态、持续膨胀；语义骨架千级、稳定。前者进后者，语义层在物理上就不可维护——每出一个新机型改一次建模，重演知识工程的死局。所以文本分两级，待遇完全不同（见下）。
## 第三部分：使命——现有 ICT 资产的语义化
### 3.1 使命的准确表述
> **语义层的使命：现有 ICT 资产（数据、知识、API）的语义化——从 ready to machine 到 ready to human。**
“现有”这个词划掉三样东西：**划掉发明**（不凭空构建本体，只翻译存量）；**划掉补全**（不以知识完备为目标，完备性压力一卸，项目从无底洞变成有底工程）；**划掉预测未来**（为还没产生的数据建模不立项）。资产原样保留，旁边长出一层双端可读的解释——**语义化不是重新建模，是贴注、锚定、翻译。资产不换，只补说明。**
### 3.2 三类资产，三种欠账
**1. 数据（含 schema）——欠“这数据是什么意思”。** `CUST_NO`、`STATUS_CD` 结构精确，语义欠费——不是设计者不在乎人，是当年机器每秒读百万次、人一年读十次，为十次的需求付命名的代价不划算。**语义层是补一次欠账，不是新建模。** 动作：继承为主，修正失真为辅，原查询照走 SQL。
**2. 知识（文本类）——欠“该站哪一层、谁签字”。** 文本无稳定 schema，横跳是常态。动作：锚定 + 换层审批 + 探针管账（见第四部分）。
**3. API——欠“调用契约的人话”。** OpenAPI 规范是给代码生成器读的；“这个接口能不能在生产环境随便调？幂等吗？超时怎么算？调错了业务上算谁的？”——这些调用契约不在任何 spec 里，在老工程师脑子里。裸 LLM 面对裸 API 会写调用但不知道哪个能碰、哪个危险、哪个该先查缓存——和数据侧“会写 SQL 不知道该查哪张表”是同一个病：**结构在，语义欠费。**
三样共同的病根一句话：**数字资产都是 ready to machine 的，智能时代要求 ready to human——业务人员和 LLM。语义化就是补这笔四十年的欠账。**
### 3.3 为什么双受众亲和是成立的
LLM 的全部能力来自预训练分布，**它的能力梯度就是人类文本的频率梯度**。人类觉得难的东西（高门槛记法、生造概念）在人类语料里必然低频，低频则模型处于分布边缘，输出不稳定。所以三者是一条链：**人难懂 = 语料低频 = LLM 弱区。** 人类的阅读困难不是体验问题，是模型性能的领先指标——**让业务人员读十分钟，他的皱眉就是模型的报错**。零成本预测，提前返工。
而且两个受众共享同一种母语，不存在“为人优化还是为机器优化”的取舍——这是和 W3C 时代本质不同的地方：当年“人读得懂”和“机器可执行”是两套语法只能二选一，现在单份自然语言建模同时服务双端。**这是 LLM 时代独有的免费午餐，也是 W3C 被终审判成双输点（人读不懂 + 机器性能差）的原因。**
## 第四部分：制度——受治理的流动性
### 4.1 文本分两级，待遇完全不同
| | **类级文本（进语义体系）** | **实例级文本（不进语义体系）** |
|---|---|---|
| 典型内容 | 口径定义、判定阈值、场景路由策略 | 手册全文、参数表、图纸、多模态资料 |
| 是否参与建模 | **参与**——挂载到实体节点 | **不参与**——留在各业务系统检索库 |
| 数量级 | 几百到几千条 | 百万到亿级，持续膨胀 |
| 维护主体 | 业务专家，按领域节奏 | 各业务系统，按型号/个体节奏 |
| 被消费时机 | **建模期就位**，定位实体即取得 | **运行期才被拉取**，穿刺到实体后触发 |
类级文本是“遇到 X 场景查哪类资料”的**路由条目**，实例文本是**被路由指向的目的地**。语义层管“去哪类”，检索系统管“哪一份”，接口是一根细细的路由指针，不是内容的拷贝。
### 4.2 运行期：明细 RAG 是被驱动的
```
问题 → 定位实体（数据架构） → 取得路由（该场景查哪类资料） → Agent 持路由到业务系统拉明细 → 执行
```
明细 RAG 不是语义建模的输入——建模期手册全文不进语义网络；也不要求语义层预先理解它——语义层只需知道“存在一类维修手册，维修场景找它”。**路由与内容分离**的直接收益是解耦：业务系统今天新增一个机型，语义层一行不用改。
反向纪律同样成立：**语义层绝不能被实例文本绑架**。数量级碾压、节奏错配（型号月级 vs 领域年级）、主体错配——W3C 系项目的经典死法就是反向失守：试图把每型每机每件都建成实例节点，图谱越建越大、越建越快失效。
### 4.3 换层制度：横跳从漂移变成移民
文本保持自由（保留横跳的可能），**挂靠关系承担定型**：每条文本登记一个挂靠——“这条知识属于哪个实体、属于哪个场景类”。承诺不在文本里，在挂靠关系里；挂靠是有型的、可寻址的、可审计的。
- **晋升**：一句随题注入的提示被反复复用、无人纠正 → 探针生成晋升候选（断言 → 共识）→ 业务专家签字，挂靠从“随用随取”改为“固定挂在实体上”；
- **降级**：共识被新个体推翻（旧标准 105 遇上新型 110）→ 分歧上浮 → 改挂靠为例外条目；
- **探针管账**：换层不能靠人记得。锚是 schema 侧的，账是探针管的，**人只签字**。
横跳从无序流动，变成有记录、有审批、有节奏的**制度化换层**——一条让文本在术语层和断言层之间合法流动、每次换层都有人签字的移民制度。
## 第五部分：验收与终局
### 5.1 双读测试（唯一的验收标准）
> **每一条语义条目必须过双读：一个不懂技术的业务人员读一遍，不皱眉；一个裸 LLM 读一遍，能执行。两条都过才入库，任何一条不过都是返工——因为人的皱眉，就是模型的报错。**
它替换掉 W3C 时代的旧标准（“推理机可判定”）。执行通道（schema + SQL）不变不翻译，解释通道（自然语言语义层）做翻译——语义层是接口的接口，一切产出最终落回执行通道才算数。这条边界守住，结构派不退化成散文派。
### 5.2 语义层永远建不完
层级既然是使用相对的，任何静态语义建模都只是对当前使用方式的快照——场景演化，快照过期。所以知识不是存货而是持续的翻译：**翻译不是语义层的美德，是使用相对性施加给它的存在方式。** 它不是一座楼，是一条制度。
### 5.3 当务之急与终版一句话
当务之急：**先找到稳定建模，语义化才有落笔的地方**——解法不发明新东西，认领数据架构，从最核心的十张表开始贴第一层人话。投资优先级上语义资产 > 模型微调：agent 换代很快，语义资产是模型无关的沉淀。
> **文本没有稳定 schema，层级在使用中赋予；所以拿企业唯一稳定的结构化骨架当参照系；骨架自身欠着人话，所以语义层的使命是：把现有 ICT 资产——数据、知识、API——语义化，从 ready to machine 到 ready to human。不发明，不补全，不重建；先立纲，后翻译，纲举目张。**
一句话的历史定位：**语义层之于智能时代，就是 ERP 之于流程时代、数据仓库之于分析时代——它不是一项技术，是对现有资产的一次系统性补课，补的是四十年里“人将就机器”欠下的那笔账。**
---
**论证骨架（五步递进）**：诊断（文本无稳定 schema）→ 参照系（数据架构为纲）→ 使命（现有 ICT 资产语义化）→ 制度（类级 / 实例级 + 换层移民）→ 验收（双读测试）——每一步由上一步推出。
