# 本体建模效果评测框架（修订提纲 v4）

基于 opencode 基线化与双范式对照的标准化评测方案 —— 围绕"怎么做评测"展开

> 2026-08-26 · 对外分享版
>
> 口径决策：
> - **DLR 不体现**——全篇只讲 ER / RDF 双范式，数字与案例均按此口径
> - 150 题实证为"同条件对照批次"；裸问/RAG 自主检索为强化设计（公开版表述待定，见第五步注）
> - 案例库仅用 ER/RDF 可讲案例（附注清单）

## 一、背景：为什么评测重要

本体+AI 的落地热潮中，各项目都在做语义穿刺——把领域知识结构化后交给 Agent——但"哪种语义建模更能引导 Agent"始终靠体感，没有客观 benchmark 衡量。

评测之所以重要，是因为三个判断都离不开它：

1. **方案选型**：ER、RDF、本体……选谁？没有对照数据就是拍脑袋
2. **能力归因**：效果提升来自 Agent 变强还是建模变好？混在一起无法归因、无法迭代
3. **资源投向**：建模工作量大，值不值得投入？需要可量化的收益证明

核心逻辑：**控制变量法**——屏蔽大模型随机性、提示词技巧等干扰，将所有表现差异唯归因于"语义底座的组织结构"。

一句话定位：**这不是 NL2SQL 评测**——NL2SQL 给定库考 SQL 能力；语义建模评测不给库，考察的是建模对 Agent 从理解问题到定位数据的全程引导。

## 二、总体架构：要解决的四个问题

评测要成立，必须先解决四个工程问题——这就是本框架的整体架构：

| # | 问题 | 解法 |
|---|------|------|
| 1 | **Agent 是变量**：大模型随机性、提示词技巧、工具用法差异会淹没范式信号 | 基线化 Agent + 上层 SOP/Skill 拉齐能力下限（第一步） |
| 2 | **信息不对齐**：两种范式若描述详略不一，测的是"谁写得全"而非"谁组织得好" | 统一语义底座，唯一变量=关联结构（第二步 · 约束） |
| 3 | **任务空间不具代表性**：题目太简单测不出引导力差异；领域单一结论不普适；对错无法判定则评测不成立 | 利用 NL2SQL 数据集满足约束（第三步 · 落实） |
| 4 | **过程不可信**：Agent 绕过底座直连库、多跑取最好、判定靠感觉 | 防作弊环境 + 全链路审计 + 人机闭环（第四步） |

架构图（deck 呈现为 arch 图）：

```
        ┌─────────────────────────────────────────┐
        │        评测工程外壳（防作弊 + 流水线）     │
        │                                          │
        │   Agent 执行中枢（opencode + agents.md    │
        │        + SOP/Skill 能力拉齐）             │
        │              ↓ MCP                       │
        │   语义底座（ER YAML / RDF TTL，          │
        │        同构存储 + 语义工具服务）           │
        │              ↓ execute_sql               │
        │   任务数据集（11 库 500 题，              │
        │        question + evidence + gold）       │
        └─────────────────────────────────────────┘
```

## 三、第一步：基线化 Agent（统一执行中枢与能力下限）

- **轻量构建**：统一 opencode 框架 + agents.md，不动底层代码
- **启发式引导**：注入自然语言规则（如"强制 /mcps 发现工具"、ReAct 闭环 "semantic → evidence ↔ mapping → SQL"），引导而非死板工作流
- **上层 SOP 与领域 Skill（能力拉齐）**：
  - 设计初衷：复杂困难问题（多表 JOIN 膨胀、SQLite 整数除法陷阱等）仅靠底层图检索可能触发 LLM 思维盲区——引入上层 SOP 指导，拉齐 Agent 解决困难问题的下限，避免 Agent 能力瓶颈掩盖建模范式效能
  - 载体：agent 目录下的领域 Markdown（即 Skill）+ MCP 工具描述层提示（如 execute_sql 的 SQLite 除法警告、大结果集提示）
  - 公平性保障：Skill 承载通用业务 SOP（如"多表查询需验证 JOIN 键的唯一性""涉及除法须显式 CAST AS REAL"），对 ER/RDF 同等开放，不含任何范式 API 偏向
  - **防背答案铁律**：知识/Skill 只写领域事实本身，禁止写对着题面的操作指令；Schema 指引不进知识层

## 四、第二步：统一语义底座（五条约束）

第二步给出的是**五条约束**——语义底座必须满足的设计要求，本身不涉及具体数据：

- **约束一 · 双范式同构建模**：
  - ER 范式：YAML 配置，BizEntity / BizAttribute / BizRelation，from→to 表达关联
  - RDF 范式：W3C R2RML .ttl 配置，rr:TriplesMap + rr:joinCondition 编码关联
- **约束二 · 描述逐字一致**：字段语义注释（ER description ↔ RDF rdfs:label/comment）内容严格对齐
- **约束三 · 知识等价**：Agent 看到的领域 RAG 知识库完全等价（同一份知识，双范式共享）
- **约束四 · 唯一变量**：唯一的区别在于关联关系表达与 Entity 归属层级不同，纯粹考验"信息组织结构"对 LLM 的引导效能
- **约束五 · 裸问**：不给 db_id、不给 evidence——语义路由与知识发现成为被考察的建模能力。**这是语义建模评测区别于 NL2SQL 评测的根本**：NL2SQL 给定库写 SQL；语义建模评测要求 Agent 靠语义底座自己定位数据

## 五、第三步：利用 NL2SQL 数据集满足约束（任务空间）

第二步给出约束，第三步回答：**NL2SQL 数据集如何被逐条利用，满足这些约束。**

### 5.1 选取：BIRD mini_dev（版本 0703）

NL2SQL 权威基准（BIRD）的精简开发版，四个选取标准：

1. **权威标注**：每题带 question + evidence（出题人规则）+ gold SQL + difficulty 分级——对错可判定、难度可分层
2. **领域多样**：11 库 10 领域（金融 / 体育 / 医疗 / 教育 / 娱乐 / 化学 / 技术 / 零售 / 游戏）——引导效果需跨业务形态验证
3. **难度覆盖**：简单查询 → 多表 JOIN → 聚合统计 → 嵌套子查询——引导力在困难题上才分得出高下
4. **规模可控**：500 题 + SQLite 单机直连——跑得完、成本可控、可复现

**关键改造 · 不给 db_id**（落实约束五）：BIRD 官方设定是"给定库写 SQL"——那是纯 NL2SQL 能力测验。本框架不给库：语义层负责从问题定位数据库，"语义路由"成为被考察的建模能力。**这一步改造把任务从 NL2SQL 转变成语义建模评测**——这是本框架与 NL2SQL benchmark 的根本区别。

### 5.2 使用方式一：改造成"模仿本体"的建模（满足约束一/二）

原始数据集只是裸表 + 题目，不能直接用于测语义建模。**改造**是核心环节：

- 逐库将原始表结构建模为两套范式配置：ER 的实体/属性/关系、RDF 的 TriplesMap（落实约束一）
- 每个字段补自然语言语义描述——值域、同名列消歧、数据特征（如"name 不唯一，同名多卡"）——Agent 面对的是**本体化的数据**而非裸表
- 双范式描述逐字一致，唯一差异 = 关联结构（落实约束二/四）

### 5.3 使用方式二：evidence 的分流利用（满足约束五/二/三）

数据集每题的 evidence（出题人规则）不直接交给 Agent（落实约束五·裸问），而是拆解分流：

| 去向 | 承载 | 例子 |
|------|------|------|
| 模型 description | 数据语义（值域、列含义、同名列消歧） | "power 三态：数字 / NULL / '*'=无限" |
| 领域知识库（RAG） | 出题人术语定义、计算公式 | "percentage = 有该属性项数 / 总项数 × 100" |

Agent 通过图检索自主发现知识——把"白送的提示"变成"Agent 必须自己找到的知识"，检索行为本身成为建模引导力的观测窗口。

**RAG 是本体建模"数据 + 知识"的闭环**：本体建模不只是静态结构，而是两件套——模型层描述"数据是什么"（在哪、值域、归属），RAG 知识库描述"知识是什么"（定义、公式、规则）。Agent 在闭环内检索知识 → 引导查询数据 → 检索与映射互相验证（semantic → evidence ↔ mapping → SQL），数据与知识联动，这才构成完整的本体建模。

### 5.4 使用方式三：高难度题目 → SOP 统一落地（对照总体架构的"统一 SOP"）

总体架构中"统一 SOP"的说法，落到任务空间里就是这条——**如何统一**：

- 利用 difficulty 标注定位困难题，失败模式（多表 JOIN 膨胀、SQLite 整数除法、百分比分母陷阱）系统收集
- 沉淀为**一份**通用业务 SOP，写入 Skill/工具层——不是给每个范式各写一套，而是同一份 SOP 对双范式同等开放，不含任何范式 API 偏向（统一 = 一份共享、两边可用）
- 效果：拉齐 Agent 解决困难问题的下限，而不泄露任何题目答案
- 实证：SQLite 整数除法（3/2=1）导致双范式全 INCORRECT；execute_sql 工具描述加一行 CAST AS REAL 警告后重跑全 PASS——"看似建模问题，实则是上层 SOP/工具层 UX 问题"

### 5.5 数据治理（满足约束的前提）

- 实测发现 20+ 处 gold SQL 缺陷（分子分母颠倒、JOIN 键写错、NULL 排序陷阱、答非所问等），逐一独立重放验证后修正 gold cache
- 教训：数据不干净，范式对照无意义——约束二/三的"逐字一致、知识等价"都建立在干净数据上，治理流程本身是框架的一部分

## 六、第四步：搭建评测工程（防作弊 + 全链路流水线）

**前置说明**：双范式底座最终都归一化到引导 Agent 生成 SQL——统一的 execute_sql 透传执行；比的是语义底座对 SQL 生成路径的引导效能，不是比"写 SQL 还是写 SPARQL"。

### 6.1 防作弊环境
- 隔离范式预知：Agent 强制 /mcps 发现工具，不预知当前挂载哪种建模范式
- 执行通道归一：execute_sql MCP 作为唯一只读薄透传通道，屏蔽底层数据库直连
- 双向堵漏（防走捷径）：
  - 架构级 · opencode 的 deny 列表：直连库、文件读写等能绕过底座的工具路径在权限层直接拒绝——后门堵死
  - 提示级 · agents.md 的提示词描述：禁止凭空猜测数据库名/表名/字段名，必须从 MCP 工具返回结果提取——前门管住

### 6.2 跑题：全迹审计落盘
- opencode 以 NDJSON 落盘每步 trace（工具调用/参数/返回），run_id 统一目录
- 意义：任何数字可回溯到原始 trace，可复现、可审计

### 6.3 解析与抽取：从 trace 到可比结果
- **双通道模板**：Final Answer 必须输出"答案通道 + Evidence SQL 通道"，解析只从 SQL 通道提取（Evidence SQL 单独执行必须直接返回答案值，计算必须写进 SQL）
- 解析失败/多 SQL/无 SQL 有明确定义（记为 EXEC FAIL），不静默丢弃
- **执行归一**：在对应 SQLite 直连执行，结果集归一化（行序/列序/NULL/浮点格式），产出可 diff 的标准形态

### 6.4 Strict 初判：秒级确定性门
- gold cache 逐行精确比对，脚本秒级 PASS/FAIL
- 定位："确定对"的快筛器，不是裁判——把 LLM Judge 算力集中在歧义样本

### 6.5 LLM Judge：语义仲裁（五环节）
- 只判 strict FAIL 的行，增量断点续跑（成本控制）
- **五环节审视**：语义理解 → 工具调用 → 映射选择 → SQL → 结果——审链路而非只看答案，是观察"建模如何引导 Agent"的核心窗口
- **证据边界**：Agent 阶段不可见 evidence，Judge 阶段可见 gold evidence 作仲裁参照——两阶段边界是防作弊设计的一部分
- **判定口径固化**：明细列表 ✓ / GROUP_CONCAT 全值 ✓ / 仅 COUNT ✗，写成文档防法官漂移

### 6.6 人机驱动：机器跑量，人做归因
- 机器做：跑量全自动、strict 判定、增量 judge
- 人做三件事：
  1. **数据集治理**：gold SQL 缺陷、evidence 伪代码——识别修正，剥离非范式噪声
  2. **翻盘归因**：INCORRECT 根因归类四类（数据集缺陷 / SOP 缺失 / 建模结构 / LLM 极限），决定"修哪一层"——5.4 的 Skill 补强实证即此闭环产物
  3. **口径裁决与定稿**：翻盘口径固化文档，归档三级对齐（raw → CSV → 汇总），单题定稿防数字漂移
- 点睛："看似建模问题，实则是 SOP/工具层 UX 问题"的判断，只有在这个闭环里才被识别

### 6.7 评测产出（双指标体系）
- **CORRECT（效果）+ token/步数（效率）**，共同刻画"引导效能"
- 汇总：agent_stats.csv（正确率、平均 token、步数分布）

## 七、第五步：阶段性观察（150 题实证，简要）

> 当前结果只是框架的一次小规模验证，不是重点。

- 规模：mini_dev 500 题已评 150 题（30%），ER 150 + RDF 150
- 指标：CORRECT ER 92.0%（138/150）vs RDF 89.3%（134/150）；平均 token ER 70,620 vs RDF 59,219（−16.1%）
- 特征画像：ER 信息全但噪音大（全互联 FK 网误导 JOIN 路径、token 膨胀）；RDF 扁平高效但无结构层级（SPARQL 嵌套膨胀、无属性归属致列歧义）
- 一个实证：SQLite 整数除法 → 工具层一行修复 → 双范式全 PASS
- 非范式问题剥离：gold SQL bug、evidence 伪代码等数据集缺陷已识别修正，不归因于建模范式
- ⚠ 批次口径注：150 题为同条件对照批次（逐题同条件，对照结论稳健）；裸问/RAG 自主检索自新批次起生效并验证。公开版表述待定。
- 方法论警示：重跑翻盘 = 有偏重采样；单题配置调优有天花板；评测结论区分"系统能力差异"与"采样噪声"

## 八、第六步：下一步

1. **完成 500 题全量评测**（含裸问/RAG 强化设计的批次验证），过程中积累对方案调优有指导意义的经验（描述形态、知识措辞、SOP 触发时机等）
2. **知识分层边界的实测积累**：哪些知识应该放语义映射的 description、哪些放实体关联的 RAG 知识库、哪些放 SOP——三层分工的边界，通过实测进一步积累
3. **探索更好的语义建模模型**：ER 信息全但噪音大，RDF 扁平高效但无结构层级——两个范式其实都有硬伤。探索是否存在更好的信息组织结构（按需暴露 + 结构化层级方向），避开两者的缺陷
