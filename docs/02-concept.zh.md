# 概念：三级语义建模（TSM）

> **一句话**：TSM 把"回答一个问题需要的东西"按**谁维护、什么时候变**分成三级——数据源级（L1）/ 领域共识级（L2）/ 业务逻辑级（L3）；**准入判据就是治理线**。
> **出身**：TSM 出自 DLR 体系的研究实践；2.0 起它是产品的**结构性原则**，与评测无关。
> 英文版：[02-concept.md](02-concept.md) ｜ 索引：[README.zh.md](README.zh.md)

## 〇、TSM + DLR 是给谁的答案

先读总论 [01-background.zh.md](01-background.zh.md)。它把问题摆清楚了：**文本是 schema-on-read 的**——同一句话在不同场景里是断言还是规则，"层级不在文字里，在使用方式里"；语义层要解决的是**赋型问题**（每条知识该站哪一层），而它的两个死法是 W3C 的"铸死"与裸 RAG 的"放任"。

**TSM + DLR 的全部设计，就是针对这些问题给出的回答**：

| 背景篇（01-background）指出的问题 | TSM + DLR 的回答 |
|---|---|
| 层级只有使用侧答案（引用频率 / 覆盖范围 / 变更节奏 / 维护主体） | **准入判据**：按使用侧问四个问题（§二）——判据是"使用方式"的可操作化 |
| 冻结派把流动铸死 → 人读不懂 + LLM 弱区 | **分层书写**：L3 用业务的话、L1 用数据的话；**双读测试**（业务不皱眉 + 裸 LLM 能执行）落在同一份自然语言上（§四） |
| 放任派（裸 RAG）层级混乱、口径打架 | **三级分离 + 判序**：`sop > consensus > 字面`，冲突有裁决者（§七） |
| 换层是常态，需要制度而不是一次性判断 | **换层移民**：挂靠定型 + 探针生成候选 + 人只签字（§二后附） |
| 实例文本亿级、语义骨架千级，不能互相淹没 | **类级 / 实例级分工**：体系只存"去哪类"的**路由条目**，内容留在业务系统，运行期经 MCP 拉取（§一·体系范围） |
| 参照系缺失 | **DLR 认领数据架构为纲**：LE-PE 双层解耦（概念 vs 落地），并行使对 schema 的 **correction 权** |

**一句话定位**：数字化时代，分层确权的产物是**文档与报表口径**（静态、要人翻译、平台升级即重写）；智能化时代，同一套分层成为**运行态资产**（agent 直接消费、有裁决序、可版本化可回归）——同一件"把秩序固定下来"的事，从"写给人看"变成"机器执行"。

## 一、框架：三级

TSM 按「谁维护、什么时候变」把回答问题所需的知识分层——这是整个框架；三级不是三种文档，而是三条确权线（见 §三）：

| 级 | 标识 | 回答什么 | 谁维护 | 变更节奏 |
|---|---|---|---|---|
| **数据源级** L1 | `dlr` | 这个领域**有什么、怎么导航**：业务对象、源提供的面、怎么连 | **数据侧** | 随 schema / 数据源演进 |
| **领域共识级** L2 | `consensus` | 题面用词**怎么算 / 怎么过滤**：术语→值、口径、背景 | **领域业务人员** | 随业务口径 |
| **业务逻辑级** L3 | `sop` | 这类问题**怎么裁**：打法、例外、陷阱 | **业务人员** | 随流程 / 打法 |

三级**并行锚定**（不是串行流程）：拿到问题后三级同时取，交叉验证后才构造答案。载体与工具属设计，见 [03-design.zh.md](03-design.zh.md)。

### 1.1 L1 = 数据源级

L1 是**数据源级知识的结构化**：把源承载的知识组织成 agent 可导航的形态。源不一定是关系表，它可能提供：

- **记录**（业务对象的表 / 视图）
- **状态**（对象及其可观测面的快照）
- **动作**（业务操作 / API，以及约束它们的文档）

三种情况的**概念是同一个**：围绕**可指认的业务对象**组织源，让 agent 按锚到达。变的只是**对象暴露哪种面**——记录、观测还是动作——不是层级本身。机制（`dlr` 与 `dlr-state` 两种 mapping 形态、记录投影、观测读法、能力契约）属设计，在 [03-design.zh.md](03-design.zh.md) 展开。

- **范围**：只到 schema 级——实例值在外（§1.2）
- **确权**：数据侧；随源变化，不随问题变化

### 1.2 体系范围：schema 进、实例出

三级的覆盖范围是 **schema 级语义**——结构、值域、粒度、术语、打法。**数据源实例级知识**（"具体某条/某批数据是什么"：客户 38508 是谁、这个月哪个产品卖得最多、这批负值都是退款……）**不在本体系的语义范畴**：

| 归体系（写进三级） | 不归体系（体系外接入） |
|---|---|
| 列的值域、表的粒度 / 样本性质、连接键（L1） | 具体行的值、**逐份快照变化的**具体实体清单、数据的实时分布 |
| 题面用词 ↔ 术语的口径映射（L2） | 只在某次查询中才知道的事实 |
| 打法 / 例外 / 陷阱（L3） | — |

> **分辨线（2026-10-10 补）**：单元里**每份快照都相同**的结构（服务名册、调用拓扑、节点名册、固定锚键、源对外暴露的动作集）属**源结构 → L1**；逐份不同的（实例名、IP、状态、报文、一次真实请求/回执）才是体系外。判据一句话：**"每份数据里都一样" = 源结构；"每份数据里都不同" = 实例。**

实例级知识的两条路：**① 即时算**（agent 用源自己的工具从数据里取）；**② 外部接入**（企业自有系统经 **MCP 工具**提供，**SOP 里引用**"这个数去哪里取"）。这样体系保持**水平、可复用**（不随数据变动而腐烂），实例事实的鲜活性交给 MCP。

### 1.3 L2 = 领域共识级

L2 装的是 L1 结构无法客观回答的部分：题面用词怎么落到模型术语、金额按本场景的什么口径算、同一措辞需要什么背景。**它建立在 L1 的对象之上**：每条都挂在 L1 的实体或面上，检索是"问题 + L1 上下文"，不是泛泛的文档搜索。

两个方向的界线都很硬：

- **L2 不重复源结构**——不写表/列名，不抄 L1 描述；关于源本身的事实（值域、粒度、样本窗口）归 L1；
- **L1 不吞题级口径**——L1 描述里一旦出现"当题面写 X 时……"，它已经浮到上层了；
- **L2 非 workflow**：不排步骤、不设截止；只在某题流程内成立的口径归 L3。

作用域问的是同一个确权问题：场景里每个对象都遵守的，是**场景级**；只对一族对象成立的，归该族；点名单个 LE 的，留在该 LE。判据见 [03-design.zh.md](03-design.zh.md) §9.1。

### 1.4 L3 = 业务逻辑级

L3 裁**这类问题**：打法、例外、陷阱与收口纪律。它引用 L1/L2 的业务名，不写物理名；按题交付，只有命中该题时才付成本。准入按需——① 数据集缺陷 ② 无节跑不对 ③ 无节 >15W——每次改节后复跑该题。

节的**形态**跟着 workload 走（见 §五 跷跷板）：NL2SQL 的 L3 薄、承担异常；agentic 诊断把每节写成决策树；长程业务运营把每节写成操作 playbook。三个场景是实测证据：

| 场景 | 源形态（L1） | L3 契约 | 结果 |
|---|---|---|---|
| `birdminidev` | 记录 | **题级结算条款**（500 节） | 500/500 评定正确 |
| `cloudopsbench` | 状态快照 | **类级决策树**（5 节） | JRA 753/754 |
| `bizagentbench` | 记录 + 动作 + 文档 | **题级 playbook + Wrong turn + 收口检查**（50 节） | strict 44/50 |

三种**节契约**，不是三种文风：单查询任务用结算条款；诊断任务用决策树；长程操作用 playbook。

> 命名注：L2 故意不叫 "knowledge"——它不是传统知识库/KG，而是**场景所需、基于 L1 schema 的一类「非 workflow」知识**。

> **层级与实现别混（重要）**：L1 是**数据源级**；**DLR 是 L1 的一种实现（本项目原创）**，不是三级的统称。`dlr` 与 `dlr-state` 是同一 L1 职责（源的有效导航）的两种 mapping 形态。L2 是**领域共识**（`consensus`），L3 是 **SOP**（`sop`）。TSM 是三级框架，DLR 只站在 L1。

## 二、准入判据（= 治理线）

一条知识该进哪级，**按序问四个问题**：

0. **它是"具体某条/某批数据"的事实吗？** → **体系外**——不写成知识（即时算，或经外部 MCP 取，见上「体系范围」）。
1. **它是数据源自身的事实吗？**（列的值域、表的粒度、样本窗口、连接键……与"谁会问什么"无关）
   → **L1 `dlr`**。哪怕它最初来自别处（比如数据集的 evidence），只要它是场景无关的源事实，就下沉到 L1，**写在对应的实体/属性描述里**。
2. **它是"题面用词 ↔ 模型术语"的映射，或只为某类说法而存在的约定吗？**（术语→列/值、公式、口径、背景知识）
   → **L2 `consensus`**。特征是：**非 workflow**，需要场景（业务）语境才成立。
3. **它是这类问题的打法 / 例外 / 陷阱吗？**（"这种题容易错在哪"、仲裁规则、检查步骤）
   → **L3 `sop`**。

**判断口诀**：

| 心里这句话 | 归入 |
|---|---|
| "这个数据怎么存" | L1 |
| "这句话查什么列 / 怎么算" | L2 |
| "这种题容易怎么错" | L3 |

边界示例：

| 事实 | 归入 | 理由 |
|---|---|---|
| `Currency` 列取值 CZK / EUR，分别是捷克克朗与欧元 | **L1** | 列的值域——任何使用此数据的人都需要，且与题目无关 |
| "monthly consumption 是逐客户逐月的聚合额，**不是**单笔金额" | **L1** | 粒度事实；写进 `Consumption` 属性描述（同时消掉"单价 vs 月消费"的混淆） |
| `transactions_1k` 只是 4 天窗口的 1000 行样本 | **L1** | 数据源自身的性质，决定了任何"某月某产品"类问题的答案 |
| 题面里的 `2012/8/24` 要按日历日期理解 | **L2** | 题面写法 → 存储格式的换算约定；不是源事实 |
| `"nationality"` 指的是站点所在国，不是客户字段 | **L2** | 题面用词 → 结构的映射 |
| "百分比题的分子分母要同口径，分母必须包含无记录的客户" | **L3** | 这类题的打法/陷阱（单题命中时才生效） |
| "客户 38508 的月消费是多少" 里的 **38508**、"本月销量第一的产品" | **体系外** | 实例级——即时从数据算，或经外部 MCP 取；不沉淀为知识 |
| K8s 里的 `worker-01`、`boutique` 命名空间；frontend 服务及其 deployment / pods / endpoints 等观测面 | **L1** | 可指认对象 + 每份快照都存在的观测面（dlr-state 形态） |
| "pod X 当前落在 worker-01 上" | **体系外** | 逐快照变化的实例事实；L2 只写"从 pods 面的 NODE 字段读落位"的读法 |

> 与旧版的差别（重要）：**"题面这句话查什么列"未必进 L2**——如果它其实是关于源本身的说明（值域/粒度/样本），按第 1 条**下沉 L1**。实践中 BIRD 的 evidence 大多属于这一类。

### L3 的加节准入（2026-09-25 定）

写一节 L3 不是免费的：节已改为**向量索引、按题检索**（`dlr_search_sop` 只取命中那一节），单节不再有全局成本——但一节仍多一份要维护、要验证的口径。所以加节有**三档准入**：

| 档 | 判据 | 依据 |
|---|---|---|
| **① 数据集错误** | 题面 / gold / evidence 自身缺陷 | 它是裁定依据，必须写 |
| **② 错题** | **没有节就答不对** | 答法/口径缺失，必须写 |
| **③ 难题** | **无节时成本显著高于带节（实测线：>15W tokens）** | 节的价值是省下探索成本 |

三档都要求**先拿到"无节基线"再判**（库里本来无节的题 = 天然基线）；跑对且成本不高的题 = 无据 → 不写节。同一把尺子也用于**回溯复核**既有节——本项目 09-25 用"摘节裸跑"的对照删掉了 debit_card 6 节无据的节。

### 判据之外：换层是制度，不是一次性判断

知识会**换层**——一句被反复复用、无人纠正的口径，就该晋升；一条共识被新个体推翻（旧阈值遇上新设备），就该降级为例外条目。所以三级不是"填一次就完"：

- **挂靠承担定型**：每条知识登记它属于哪个实体 / 哪个场景类——承诺不在文本里，在**挂靠关系**里（可寻址、可审计）；
- **探针生成候选**：谁在被反复引用、谁在被反复纠正，由运行观测产出候选（原料 = 会话日志 / 考卷结果，见 [eval.zh.md](eval.zh.md)）——不靠人记得；
- **人只签字**：晋升 / 降级的决定权在 owner（§三），机器只把候选递到手边。

（本项目里 L3 的"事后准入"就是这套制度的雏形：运行暴露问题 → 归类 → 补条目。**横跳从漂移变成移民**。）

## 三、分层确权：企业级的骨架

TSM 对企业最实际的意义不是技术，是**确权**——"上帝的归上帝，凯撒的归凯撒"：

- **业务人员**维护自己的 `sop`（口径、例外、流程，用业务的话写）；
- **领域业务人员**维护 `consensus`（术语、领域共识）；
- **数据侧**维护 `dlr`（数据源本身的样子，随库演进）。

三线各有责任方、各有变更节奏、互不污染。由此得到一条**书写纪律**：

> **文本的分层就是权属的分层**：L3 通篇业务语言、L1 通篇数据语言、L2 居中做对齐。

## 四、分层书写原则：引用下级，不越级描述

好的分层 = **上层可以引用下级的对象描述；层层对齐、层层收敛；不要越级描述**（2026-09-20 定）。

- **L3 不写库表列原名**（不出现 `yearmonth`、`Consumption`、`transactions_1k` 这类词）。需要指涉某列时，用业务语言说"我要什么数据"，物理映射由 L1/L2 提供。
- **数据自身的约定可留**（如"期间记录为 YYYYMM 编码"），**库表结构描述不留**。判断标准：这句话是业务在说需求，还是数据库在自我介绍？
- 反面教材：某条 L3 曾把"每行 = 某客户某月"写成 `yearmonth.Consumption` 级别的数据源描述——**越级**。
- 同理，**L1 不写题面口径**（那是 L2/L3 的事）；一旦 L1 描述里出现"题目里写 X 时……"，就该上浮或删掉。

**验收 = 双读测试**（每条语义条目的唯一标准）：一个不懂技术的业务人员读一遍**不皱眉**，一个裸 LLM 读一遍**能执行**——两条都过才入库。这不是体验问题：**人难懂 = 语料低频 = LLM 弱区**，业务人员的皱眉就是模型的报错，而且是一次零成本的提前返工。

**correction 权**：语义层不擅动 schema，但对 schema 的**描述**享有修正权——"此表名为 X 实为 Y，历史原因，按 Z 理解"。**译者不改编原著，但译者有资格指出原文的笔误。**

> ⚠ **本项目的边界（2026-09-24）**：使用数据集建模时**不做语义丰富度补充**（公平性）——描述一律取自数据集原生；数据集自身的缺陷**不在 L1 修**，交 L3 承载并**标注类型**；correction 仅限"消除歧义所必需"的最小措辞。见 [04-application.zh.md](04-application.zh.md) §二。

## 五、层重随 workload 跷跷板

三级的**投入比例不是固定的**，由负载形态决定：

| workload 形态 | L1 | L2 | L3 |
|---|---|---|---|
| NL2SQL / BI 问数 | **重**（数据源语义是主要矛盾） | 薄 | 极薄（仅仲裁） |
| 运维 / agentic（如 RCA 类） | 薄在属性深度（无列级属性；对象 / 面 / 边仍建模） | 按需 | **厚**（按症状族组织的决策树；节少不等于薄） |

同一套 TSM 吃两种形态，靠的就是分层解耦——**投资哪层由 workload 决定**，不是把三层都填满。

> **COB 是这一端的实证**：L1 没有列级属性，但对象 / 面 / 边并不少——**169 LE / 355 PE / 233 PAS**（两系统）；L2 15 条；L3 只有 5 节，却覆盖 754 例——因为每节不是一条答案，而是一棵**决策树**（见 §六「逐层消歧」）。**「L1 薄 / L3 厚」说的是形态，不是节点数或节数。**

关于 L3 的两个认知（避免低估）：

- 它在本项目（NL2SQL）里薄，是因为 **NL2SQL 太简单**（单查询任务，没有流程可写）；它同时充当**异常承载层**（建模冲突、题面缺陷、陷阱的仲裁）。
- 但**bench 证明不了 ≠ 不重要**：对企业，L3（业务逻辑）**可能是最重要的一层**——L1 是门槛（工具多、可替代），L2 是词典，L3 才是"我们的数按我们的口径算"的独有资产。

## 六、层职能与上限（难题怎么落地）

三级的职能各有边界；一级配不齐的，**往上开一级，不在本级硬堆**（2026-10-12 定，RCA 场景跑批收敛）。运行态三层**并行召回**（§一）；本节讲的是**开发态**——模型撞上限时怎么扩展。

### 逐层消歧：每层只解决本层能客观判定的事（2026-10-19 补）

三级不是三份并列的说明，而是一条**逐层消歧链**：每层尽量只做本层能客观判定的事；一层解决不了的，**不在这一层死磕，向上开一层**——硬压会把问题挤到另一层弹回来（按下葫芦浮起瓢）。

- **L1（`dlr`，DLR 是它的一种实现）内部：物理表 → PE → LE。** 物理表天然有歧义（碎表、宽表、同名异义列、多槽位 FK）；PE 用**视图**消歧（圈定行、选列、定锚、注语义）；PE 仍有歧义（这个面属于哪个业务对象、哪个 public 面是寻址点）→ LE 用**可指认的对象 + public 面 + PAS** 消歧。这是 L1 内部的两级消歧，详见 [03-design.zh.md](03-design.zh.md) §0。
- **本层建模消不了本层的歧义。** L1 是水平建模：语义网络一大，不同提问者的自然语言用词不同，**向量相似的实体未必是目标实体（相似 ≠ 目标）**。这不是 L1 没建好，而是 L1 只回答"数据怎么存、有哪些对象"，不回答"这句话指的是哪个对象"——题面语言 ↔ 模型的映射天然超出 L1 的客观范围，必须到 L2 消歧（术语 → 列/值、同义/多义、领域口径）。L2 消完术语歧义后，L1+L2 与题目语义仍可能有真实冲突（两种口径都成立 / 数据与共识不符）→ L3 题级裁决。
- **跨级：L1（`dlr`）→ L2（`consensus`）→ L3（`sop`）。** L1 只能客观回答"数据怎么存"；题面用词 ↔ 模型的映射、领域口径不在 L1 的客观范围内 → L2。L1 + L2 仍会有天然冲突：有的冲突是业务上**真实存在**的（两种口径都成立，取决于题意），有的是**系统级**的（业务没问题，但数据与共识对不上）→ L3 做题级裁决。
- **L3 内部再分层（COB 实证）。** SOP 若只有"一层"——一节直接给一个答案——同样会歧义：同一症状措辞下可能是多个机制。COB 的 SOP 因此把一节写成**决策树**：① 节标题 = 症状措辞（先锁定哪一族）→ ② 节内分支 = 链上实际观测落到哪个机制（Pending / 镜像拉取 / 准入 / 路由……）→ ③ 链序与收口 = 机制事件 + 事件面 + 配置三件套（防止"机制对但证据链不闭合"）。**5 节覆盖 754 例，不是节少，而是每节内部有分层。**

> 与 §五的「层重跷跷板」区分：§五说的是**投资比例**随 workload 变化；这里说的是**层间上限**——本层硬压会把问题挤到另一层。两者是同一分层设计的两个侧面。

> **前瞻：L2 也会随 LE 分层（方向，未验证）。** 当前两个 benchmark 都不适合展示这一点；但一条 SOP 口径若是**全局成立**的，就可以自然下放到 L2（按 LE / 域组织）；只在某个 LE 内成立的口径则按 LE 隔离。**分层消歧与按 LE 隔离，是同一治理工具的两种用法**——见 [roadmap.zh.md](roadmap.zh.md) §五。

**每层的职能与上限**：

| 级 | 首要职能 | 不是它的活 |
|---|---|---|
| L1 | **保证寻源正确**——有什么对象、落在哪、怎么取，读法指对源 | 不承担题级判断；描述里吸收额外领域共识只是**加分项** |
| L2 | **按条补充**——schema 级读法、术语口径，按需一条条生长 | 题级走序装不进条目——"什么时候读"不是读法问题 |
| L3 | **题间冲突的裁决**——同一读法在不同题下结论相左时的定夺（打法 / 例外 / 收口纪律） | 不进答案、不逐题写：按题面措辞族分节，未暴露成本的措辞不写节 |

**每层的上限**（撞上限 = 该级结构性配不了，换级才解）：

- **L1 上限 = 结构**：能表达"有什么、怎么读"，表达不了"怎么走"——链序纪律在 L1 结构上不承载。
- **L2 上限 = schema 级**：读法全对，agent 仍可能把收口读法当探针提前用——顺序不是读法条目能配的。
- **L3 上限 = 泛化红线**：绝不由答案倒推；残余失分撞到"再往上没有层可追"（已不属任何级的缺陷）——留观，不调参扑评分器。

**难题落地流程**（实操定式）：

1. **先解剖，再动手**——沿会话 trace 找第一个"观测 ≠ 期望"，判定失败机制住在哪级；不猜、不先改。
2. **按机制分诊**——缺陷在本级就在本级修（读法指错源 → L1；该有的条目没有 → L2）；"怎么走"缺打法 → L3；读了也不走收口 → **宿主行为规则**（AGENTS 层）。
3. **最小修**——一次一个实体 / 一条条目；牵动整批读法模板的横切改动单独评估。
4. **复跑对表**——改完必须复跑暴露问题的题；**跑对不算完**：还要在未经解剖的同类题上验证泛化——防"把答案写进知识层"。
5. **留档与停止线**——记定性观察 + 提交；未收敛就停下来报方案，不无限重跑；不扑评分器。

> 反过来：**上层不代偿下层**——L1 读法指错源，L3 再写也补不回；爬梯的前提 = 下级已尽力且干净。本项目实例（RCA 场景）：载体资源误写 = L1 修；收口读法被当探针提前读 = L3 补；机制读到但不走收口 = 行为层兜底——三处各修各级，互不代偿。

> **对偶**：运行态按**判序**裁决（§七：`disputes > sop > consensus > 字面`）——建好之后的仲裁；开发态按**上限爬梯**——建设中的扩展。一个对题，一个对失败。

### Agent 运行态设定——知识供给的另一半（2026-11-03 提级）

三级解决的是**知识供给**：有什么（L1）、怎么读（L2）、这类题怎么打（L3）。但知识供给本身不会让 agent 去用它——还需要一份**运行态操作层**：场景的 `AGENTS.md` + 运行配置（人格、工具面、结果剪裁、禁用项）。它不是可选项，而是每个场景包的一等交付物。

- **绑定判序**：L3 exact > L2 > L1 > 模型先验；每题开局先检索 L3，收口前回读。没有这层，L3 只是“又一段上下文”，写得再对也会被模型自己的计划盖过。
- **绑定执行纪律**：时钟/顺序、逐请求批准、账单 vs 行、带符号调整、未用额度释放、核验后单次收口。
- **实测背书（RCA 场景）**：`AGENTS.md` 的症状先行 / 锚后回查 L1 / 收口三件套 / 提交契约，加上运行配置，把 EOC/ECR 从 0.25/0 拉到 1.0；同样的 L3 内容没有这层设定时不成立。

## 七、答题时怎么用（给 agent）

1. 先判断"这题缺什么"：**缺结构** → L1；**缺口径/术语** → L2；**缺题级判断** → L3。
2. 三级**并行发出**，交叉验证后再写 SQL；L1 召回可能排错，L2/L3 用来纠偏。
3. **判序**（冲突时）：`disputes > SkillPath(SOP) > KnowledgePath(consensus) > 源字段字面`；L3 严格命中本题即最权威。
4. 结论必须可追溯（工具返回 / SQL 结果），并注明来源。
5. **上面的判序是运行态契约**：必须写进场景的 `AGENTS.md`；仅靠检索不会自动建立权威——没有运行态设定，agent 会把 L3 当可选背景。

> 具体协议见 `DSH-based Agent Service/AGENTS.md`（执行入口）与认知技能 `skills/paradigm`；本文不重复。

## 八、常见误读

- **把 L2 当"证据库"**——它是口径与术语，不是明细数据；"evidence" 是数据集字段名，不是范式术语。
- **把 L1 当"随便写的描述"**——L1 只承载源事实；任何题面耦合的表述都不该留在 L1。
- **把 L3 当评测补丁**——它是业务资产的正式载体；缺陷仲裁只是它在 NL2SQL 形态下的副产品。
- **认为三层都要填满**——层重随 workload 跷跷板（第五节）。
