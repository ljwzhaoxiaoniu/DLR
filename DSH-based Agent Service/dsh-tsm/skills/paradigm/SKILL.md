# 范式认知：TSM 与 DLR（与数据集无关）

## 1. 三级语义建模（TSM）：知识放在哪一级

| 级 | 载体 | 回答什么 | 怎么拿到 |
|---|---|---|---|
| L1 数据源级 | DLR 语义图谱（LE / PE / ARC） | 这个领域**有什么**：业务概念、落地在哪、怎么连 | `mcp__semantic-core__dlr_semantic_query` → `get_pe_mapping` / `get_le_attrs` |
| L2 领域共识级 | 领域共识条目（带 `kid`；基于 L1 schema、**非 workflow**） | 题面用词**怎么算 / 怎么过滤**：术语→列值、公式、口径 | `mcp__semantic-core__dlr_search_consensus` |
| L3 业务逻辑级 | `sop` 检索索引（随场景构建） | 这道题**怎么裁**：题干级口径与陷阱 | `mcp__semantic-core__dlr_search_sop(question)` |

**判序**（冲突时）：题级仲裁（L3）> 领域共识（L2）> 你自身的常识。L1 只提供结构，不提供口径。

## 2. DLR 数据源级：LE / PE / ARC

- **LE（逻辑实体）** = 业务概念层，与物理库解耦，跨库统一索引。**同名概念在不同库可以是不同 LE**——歧义靠 LE 边界隔开语义，而不是靠字段名区分。
- **PE（物理实体）** = 概念的物理落地（一张表 / 一个记录集），绑定一个物理库；`database_url` 是 PE 级字段。
- **一个 LE 可以挂多个 PE**（同一业务概念的不同粒度 / 不同落地）。`dlr_semantic_query` 已在 **LE 层归并**（同概念不重复占召回名额），并给出 LE 级统一属性视图 `public_attributes`——它只是统一入口，**真实列名与格式必须下钻到 PE**。
- **ARC** 是关系表达，四个槽位：

| 槽位 | 含义 | 答题时的用法 |
|---|---|---|
| `A_anchor` | 锚键 + 基数（如 `N:1`、`1:1`） | **JOIN 的依据**：同 LE 下多 PE 共享锚键；跨 LE 时锚键同名即可直接 JOIN，不同名则需 PAS 路由（本工具面未注册路由工具，遇到时用 L2 证据判断） |
| `R_row` | 行级关系 | 可能为空 = 本库未使用 |
| `C_column` | 逻辑属性 → 物理列的全限定映射 | L1 语义 → SQL 列名的**唯一翻译表** |
| `S_semantic4arcs` | 人读的语义说明 | 辅助理解，不参与推导 |

## 3. 信息分层暴露（刻意的设计，不是缺陷）

`dlr_semantic_query` 的返回**不含**物理表名与 `database_url`；只有第二跳 `get_pe_mapping(pe_id)` 才给。这是用信息不对称强制「元数据走 MCP、数据走 SQL」的顺序——不经过 PE 这一跳，就写不出可执行的 SQL。

## 4. 答题时怎么用这套认知

1. 先判断"这题缺什么"：**缺结构** → L1；**缺口径/算法** → L2；**缺题级判断** → L3。
2. L1 召回后锁定 `db` 与候选 LE；对候选下钻 `get_pe_mapping`，重点看三样：锚键与基数、`C_column` 映射、`database_url`。
3. **JOIN 的合法性来自锚键**（不是来自"表挨得近"）。
4. 写 SQL 前对照 `sop`：题级口径若与 L2 通用公式冲突，**以题面用词与数据自身粒度为准**。
5. 结论必须能追溯到具体数据（工具返回 / SQL 结果），并注明来源。

## 5. 常见误读（避免）

- 把 `public_attributes` 当"真实列"——它只是 LE 级统一名，列名与格式要到 PE 看。
- 把同一 LE 的多个 PE 当多个概念——它们是同一业务概念的不同落地。
- 把 L2 的通用公式当铁律——当数据粒度与公式冲突时，以数据为准（`sop` 会点名这类情况）。
- 跨库串扰——`dlr_search_consensus` 的 `namespace` 留空是**跨库召回**（还没定库时探路用；命中自带 `namespace` 与它派生的原题 `question`，对得上才采信），**定库后必须传库名收口**，别拿别库的共识当本题规则。
